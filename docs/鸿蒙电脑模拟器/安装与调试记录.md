## 为什么新建一个目录还不够

父目录就是路径的上一级。例如 `/codex/config.toml` 的父目录是 `/codex`，`/codex` 的父目录是 `/`。

配置、项目和普通日志可以集中到一个专用目录，但当前程序的受保护运行目录是编译时约定，并不随 `CODEX_HOME` 改变。它还会检查各级父目录，防止运行文件和控制套接字被其他身份替换。

当前模拟器的 `/` 挂载为只读，当前身份也无权在根目录创建 `/codex`。即使某个可写位置可以建立专用目录，也不会因此获得读取内核控制文件、创建隔离环境等系统权限。没有修改整个 HOME 或系统目录权限，没有关闭系统安全策略，也没有自动改为完全权限。

## 正式适配目录的依据

应用文件应从实际应用的 `Context` 获取：持久数据使用 `filesDir`，缓存使用 `cacheDir`，临时文件使用 `tempDir`。官方明确区分应用的沙箱路径与 hdc 的系统进程视图，并要求通过 Context 获取目录，不能只拼接固定路径。[官方应用沙箱目录说明](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/file-management/app-sandbox-directory.md)

因此，后续目录方案必须同时确认启动身份和宿主：原生 CLI 从 HiShell 启动时，需验证该宿主实际可用的私有目录；若采用原生应用宿主，则由该宿主获取自己的目录并建立经过校验的运行约定。把 ELF 文件复制到某个应用路径，不会自动创建应用上下文或获得其权限。

本机 SDK 提供 `OH_AbilityRuntime_ApplicationContextGetFilesDir` 等 C 接口；其文档说明应用上下文可能不存在，包括应用创建的子进程。因此不能承诺独立 CLI 直接调用就能成功。[官方 C 接口说明](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-ability-kit/capi-application-context-h.md)

本次探针在普通 hdc Shell 中尝试三个 Context 目录接口，均在加载依赖库 `libark_jsruntime.so` 时失败，未执行到成功获取目录。这进一步表明还需要正确的宿主运行环境，不能把路径 API 当成授予权限的入口。目录可写、原生子进程可执行和 bwrap 隔离可用必须分别验收；暂不将普通应用宿主认定为已经验证的完整方案。

## 初次候选包检查命令（历史）

在 Mac 终端执行：

```bash
# 使用 DevEco 自带的连接工具。
export PATH="/Volumes/MacSSD/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/toolchains:$PATH"
# 查看已经安装的原生 Codex 版本。
hdc -t 127.0.0.1:5555 shell '/data/local/tmp/codex-emulator/real-pc-candidate/bin/codex --version'
# 进入模拟器的交互式调试 Shell。
hdc -t 127.0.0.1:5555 shell
```

以下命令在进入模拟器 Shell 后执行；它会重现当前启动阻塞，**不是已经打通的聊天入口**：

```sh
# 指定已同步的配置目录，保留配置中的 gpt-5.6-terra 模型。
export CODEX_HOME=/data/local/tmp/codex-emulator/state
# 使用新建的测试项目目录。
cd /data/local/tmp/codex-emulator/workspace
# 尝试启动；当前候选包预期在运行目录校验阶段退出。
/data/local/tmp/codex-emulator/real-pc-candidate/bin/codex
```

后续需要验证适合原生执行的应用或终端宿主及其私有目录，并分别复测目录保护与 bwrap 启动。官方提供 `hdc shell -b` 调试应用目录入口，但要求已安装并启动的调试签名应用；该入口是否允许当前 Codex 所需的任意原生执行仍需验证，不能直接视为解决方案。[官方 hdc 说明](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/dfx/hdc.md#执行交互命令)
