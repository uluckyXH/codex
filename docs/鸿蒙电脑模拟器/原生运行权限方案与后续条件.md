# 原生运行权限方案与后续条件

日期：2026-10-04。范围：当前鸿蒙 7 PC 模拟器。目标仍是原生 Codex，固定模型 `gpt-5.6-terra`；这份文档不宣称已完成正常对话和工具操作。

## 已明确的原因

| 现象 | 已确认原因或失败位置 | 对应处理 |
| --- | --- | --- |
| `.codex`、别名或控制目录初始化失败 | HDC UID 2000 的目录归属与真机 HiShell 不同，旧包使用另一种目录约定 | 显式 `hdc-debug` 构建，仅认可已验证的固定祖先与私有运行根，现已通过配置和会话启动 |
| headless 命令长时间等待 | Codex 会追加管道标准输入，而 HDC 没有给 EOF | 无需输入的 `codex exec` 命令加 `</dev/null`，已复测立即启动 |
| TUI 终端模式设置 `EACCES` | 继承的 HDC stdin 虽是 TTY，但 `tcsetattr` 被拒绝；重新打开 `/dev/tty` 后可设置和恢复 | 专用启动脚本重新打开当前控制终端，保留失败退出 |
| TUI 没有文字画面 | HDC 远端终端报告 `0×0`，系统拒绝 `TIOCSWINSZ` | 由 Mac 入口传实际窗口尺寸，OHOS 界面仅在原生尺寸无效时使用合法提示；完整联调结果单独留档 |
| 模型请求 `error sending request` | 实际 `POST /responses` 在 TCP `connect` 返回 `PermissionDenied, os error 13` | 按受支持的应用/终端身份处理联网权限；已有 CA 加载成功，尚未到 TLS 握手 |
| 受限工具退出 1 | 当前镜像 user namespace 调用 `EINVAL`，Landlock ABI `ENOSYS`；修复 bwrap 前置读取后仍无法建立隔离 | 当前内核不能运行现有受限后端；不能用关闭校验或自动完全权限冒充修复 |

文件可写、网络可用、外部程序可执行、命令隔离是独立条件。目录名改成 `/codex` 不会增加其他能力，根目录在本镜像也不可写。

## 两条正规运行路线

### 保留独立 CLI 与终端宿主

原生独立 ELF、完整工具和现有 CLI 结构继续保留。需要在实际 HiShell/DevBox 或官方支持的终端宿主中确认目录、进程权限与二进制执行策略。华为建议 `/data/local/tmp` 用于 HDC 临时测试可执行文件，但并未承诺它提供应用的全部权限。[官方调试目录问答](https://developer.huawei.com/consumer/cn/doc/doccenter-dev-faq/faqs-performance-analysis-kit-41.md)

本轮 HDC shell 的 `u:r:sh:s0` 与真实 HiShell 不同。HDC 的 TCP/Unix socket 拒绝不能直接替代真机结论，真机已有的命令 159 和文件失败仍须分别验收。新版自签名包没有权限段；若选择独立二进制声明权限，需要正式证书签名流程。

需要准备的材料：

1. 从华为官方入口申请、适用于本项目及目标场景的二进制证书链。
2. 与证书匹配的本地密钥库、密钥别名和所需口令。
3. 按官方签名及应用分发流程需要的配套配置；是否涉及特定权限和 Profile 必须按实际场景核对。
4. 最小权限声明文件，例如只需要联网时的 `requestPermissions` 中声明 `ohos.permission.INTERNET`。

密钥库、私钥和口令不提交 Git，也不直接发进聊天正文。提供本地材料路径后才能验证签名结果；目前没有完成证书申请或证书签名验收。正式签名也不能自动覆盖 SELinux 规则或补齐内核 namespace。

官方入口：[二进制签名工具](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/binary-sign-tool.md)、[申请二进制证书](https://developer.huawei.com/consumer/cn/doc/app/agc-help-binary-cert-0000002408063605)。申请页面需要在官方账户中完成，本文没有代替用户登录或承诺申请一定获批。

### 使用普通鸿蒙应用宿主

应用通过真实 `Context.filesDir`、`cacheDir` 和 `tempDir` 管理自己的数据，只声明必要的普通权限。当前最小原型已证明：`INTERNET` 应用通过 `OH_Ability_StartNativeChildProcess` 启动正常打包的 `.so` 子进程后，公开域名 TCP、私有文件读写、系统 Shell 与 PTY 均可用。

后续的官方 private HNP 实验已经进一步验证：原样的 SDK 自签名原生 ELF 随普通调试 HAP 安装后，可由应用正常 `posix_spawn`，并成功连接公开域名。安装前后 ELF 摘要相同。因此当前选用 HNP 安装完整 Codex 的路线，保留真实 `codex_self_exe` 和原有助手布局，无需把 Codex 改成共享库或冒充宿主可执行文件。

本应用的真实 ApplicationContext 文件目录为 `/data/storage/el2/base/files`。系统初始提供的应用 `base` 和 `files` 权限是 `0777`；仅在我们专用调试应用内，通过原生 FD 将这两级收紧到 `0700` 后，父进程与 HNP 子进程检查一致，停止并重新启动应用后保持。其他应用、用户 HOME 和系统目录没有修改。新建的短运行根 `files/r` 也为 `0700`；Codex 不增加接受任意 `0777` 祖先的例外。

应用不能动态创建符号链接，HNP 调试包因此预装四个小型自签名工具入口，保留正常 Codex 自执行和参数转发。实际安装器使用 UID/GID `3060:3060` 的 `0775` 目录；入口校验只在 `/data/app` 子树认可这一精确的系统安装器身份，并要求应用及其附加组不含 `3060`。可执行文件保持不可被组或其他用户写入，继续校验每级路径、FD 身份和编译时绑定摘要。这个安装目录契约不应用于用户数据目录。四个原生入口及目录/锁/完整摘要套接字测试已在应用内通过，完整 Codex 仍待新包测试。

构建策略 `hnp-debug` 绑定当前应用 UID 和固定 30 字节运行根。应用安装身份变化时必须重新核验，不把这个包冒充通用 HiShell 包。模型配置由应用私有入口单独导入，不能包含在 HAP/HNP 中；最终配置须为 `0600`。

适配顺序：目录契约测试 → 完整 Codex 与助手的 HNP 打包 → 私有配置导入 → 真实 Responses 响应 → 分别验收命令、文件、交互及生命周期。最小程序联网成功不等于完整 Codex 已通过这些验收。

此前普通数据目录中的独立自签 ELF 被拒绝，属于另一种部署方式。华为 IDE 扩展问答中关于弱沙箱权限和用户设置的条件，不直接套用到已经实测成功的官方 private HNP 安装路径。[官方 IDE 扩展要求](https://developer.huawei.com/consumer/cn/doc/doccenter-dev-faq/faqs-access-control-23.md)、[官方 HNP 原生包机制](https://github.com/openharmony/startup_appspawn/blob/master/service/hnp/README_zh.md)

## 沙箱与用户选择

本镜像已测的 user namespace/Landlock 缺失是单独条件。应用身份下包内 bwrap 版本启动通过，但受限命令仍在创建命名空间阶段以 `EINVAL` 退出 1，命令未运行。完全权限模式可以作为用户明确选择的测试方式，但仍受鸿蒙应用权限与系统策略约束；也不会解决 HDC 的 TCP 连接拒绝。

只操作专用工作区是一条测试约束，不等于内核隔离。未收到明确选择前，入口和本次模型调用均保留原有/只读沙箱设置。也没有关闭 SELinux、修改系统账户或整个 HOME 的权限。
