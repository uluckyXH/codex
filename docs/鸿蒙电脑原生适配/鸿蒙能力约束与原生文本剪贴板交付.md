# 鸿蒙能力约束与原生文本剪贴板交付

本次为原生 OHOS CLI 加入能力边界和公开 API 文本剪贴板后端。源码验证完成，真实商业鸿蒙 PC 能力仍待设备验收。最终源码以本文件同批提交及[最终测试报告](测试报告/2026-10-02-205738-鸿蒙能力最终定向验证-终端会话/测试报告.md)中的摘要为准，基线为 28ff2f12846dd34b302ee64f4a2c95fa7a4c8d38。

## 已落地的行为

| 能力 | 原生 OHOS CLI 行为 |
| --- | --- |
| code_mode / host / prewarm / interrupt / only | 默认关闭；显式配置和运行期启用返回具体不支持原因；宿主启动和会话创建入口再次拒绝 |
| 模型 metadata 指定 Code Mode | 使用 direct 工具并提示缺失宿主；不会因此清空 shell、文件等本地工具 |
| 定制 zsh exec bridge | shell_zsh_fork / unified_exec_zsh_fork 不可用；普通原生 shell 与 unified exec 仍保留 |
| 语音与听写 | 内建功能关闭；实时会话与 VoiceHost 启动前明确拒绝，不访问音频设备 |
| 内建桌面/浏览器自动化 | 内建相关开关关闭并拒绝强制启用；普通 MCP 工具不受此表禁止 |
| 复制文本 | 用户操作时动态加载 libpasteboard.so / libudmf.so；原生成功才确认复制；失败时沿用明确未确认的 OSC 52 后备结果 |
| 粘贴文本 | 可显式开启右键读取；要求系统库和进程获准访问剪贴板；失败显示原因和错误码 |
| 剪贴板图片 / HTML | 本次未实现；Markdown 复制只保留纯文本内容 |
| 浏览器自动唤起 | 返回 Unsupported，并保留供手动打开的 URL；没有调用 Linux 桌面启动器或外部脚本 |

功能边界集中在 codex-rs/features/src/platform.rs。原始配置请求保留用于校验，同时 Features::enabled 不会将缺失能力暴露为已开启。实验功能列表和提示过滤了这些入口。

## 诊断与终端使用

下面的命令是交付接口说明，本会话没有运行 CLI 或读取用户配置：

```sh
codex doctor --capabilities --json
```

该分支跳过 Config 加载与认证、网络、设备诊断，只列出编译能力限制、当前进程来源、搜索工具路径和未探测事项。正常 CLI 启动环境初始化仍会发生：进入该分支之前，arg0_dispatch 已调用 load_dotenv()。因此不能把 report() 的隔离范围扩大为整个进程不读取配置或凭据相关环境文件。诊断中的“存在”只指路径或代码；不会把宿主可执行性、剪贴板权限、音频或设备运行记为已通过。

普通终端粘贴快捷键保持可用。需要原生文本右键读取时可配置：

```toml
[tui]
right_click_paste = "on"
```

OHOS 的 Auto 仍关闭，避免默认读取未经确认的系统剪贴板。SSH 和 VS Code 终端的所有权限制仍生效。系统返回权限错误 201 时显示 ohos.permission.READ_PASTEBOARD 要求；该设置本身不会授予系统权限。

## 原生 API 依据和边界

本机 DevEco Studio Native SDK 6.1.1.125 / API 24 的 database/pasteboard/oh_pasteboard.h 提供 API 13 的 OH_Pasteboard_Create / Destroy / SetData / GetData。UDMF 的 Data、Record 与 PlainText API 用于纯文本对象，C ABI 探针核对并链接了实际使用的全部 15 个符号。头文件为 GetData 标注 READ_PASTEBOARD 权限。所有对象在原生调用后配对释放；读取输出按消息长度限制复制、校验 UTF-8。

Huawei 官方入口：[Native 剪贴板指南](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/native-use-pasteboard)、[ApplicationContext C 接口](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/capi-application-context-h)。本次网页工具只返回动态页面外壳，未据此虚构正文；实际签名以已安装 SDK 头文件为准。

同时阅读了上游 [OpenHarmony Native 剪贴板指南](https://raw.githubusercontent.com/openharmony/docs/master/en/application-dev/basic-services/pasteboard/native-use-pasteboard.md)及[公开 C 接口文档](https://raw.githubusercontent.com/openharmony/docs/master/en/application-dev/reference/apis-basic-services-kit/capi-oh-pasteboard-h.md)，用于核对库名称、对象生命周期和权限模型。此类应用 API 文档不构成普通终端进程已获授权的证据。

浏览器部分检查了 SDK 的 AbilityKit/ability_runtime/application_context.h。该公开 C 接口提供 StartSelfUIAbility 系列，面向当前应用的 UIAbility 与应用上下文；本次没有找到适合独立 CLI 的通用浏览器 URL 启动接口。因此保留明确不支持，不采用内部命令、猜测接口或辅助脚本。结论限于本次检查的 SDK 与 CLI 形态，不宣称所有未来鸿蒙 API 都无法实现。
