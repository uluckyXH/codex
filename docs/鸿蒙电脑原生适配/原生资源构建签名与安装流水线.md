# 原生资源构建签名与安装流水线

本页说明已经落地的构建入口。目标为 ARM64 商业鸿蒙 PC 的原生 CLI 候选包，不经过 Linux 子系统。Mac 可以完成交叉编译、签名和静态检查；商业设备能否加载、执行子进程及建立隔离，仍需实际型号和系统版本的验收。

## 构建顺序为什么不能交换

1. 从锁定源码构建 OHOS `libcap`、`rg` 和仓库内的 `bwrap`。
2. 使用 SDK `llvm-strip` 处理辅助程序，再用官方工具自签名。
3. 计算**签名之后**的 `bwrap` SHA-256，通过 `CODEX_BWRAP_SHA256` 编入 CLI。
4. 完整构建 release CLI，剥离符号，然后自签名 CLI。
5. 构建并签名独立目录探针；将四个签名文件原样复制到目录包，检查 ELF、摘要、资源、许可，再归档，生成压缩包 SHA256 文件。

不能在第三步后重新签名或修改 `bwrap`，否则运行时完整性检查会拒绝它。随包沙箱仍通过已校验的文件描述符执行；没有为了适配签名而取消摘要校验或改成存在路径替换窗口的启动方式。该描述符执行入口在商业设备上的签名接受条件尚未验证。

## 依赖和宿主环境

按[外置盘配置](苹果电脑构建环境与外置盘配置.md)设置 Rust 和 Cargo。新增流水线使用 Python 3.12 或以上、宿主 C 编译器、Java 8 或以上、带原生工具链与 `binary-sign-tool.jar` 的完整 DevEco SDK。本次实际使用 Python 3.14.7、Java 17、Rust 1.95.0、Native 6.1.1.125 / API 24。SDK API 号不等于最低支持的商业系统版本。

构建源码和缓存来源：

| 组件 | 固定来源 | 摘要及处理 |
| --- | --- | --- |
| libcap | kernel.org 的 2.78 源包 | 脚本内固定 SHA-256；生成名称表的程序在 Mac 执行，库本身由 OHOS Clang 编译为静态库 |
| ripgrep | crates.io 的 15.2.0 源包 | 脚本内固定 SHA-256；按随包 Cargo.lock 构建 OHOS release，使用默认特性，不启用 PCRE2 |
| bubblewrap | 本仓库 codex-rs/vendor/bubblewrap | 来源随 Git 提交固定；仅 OHOS 加入目录接口兼容层，静态链接目标 libcap |
| 系统库 | 所选 SDK 的目标 sysroot | 只参与链接，不能将 SDK 桩库作为运行库复制给用户 |

源码缓存损坏会直接失败；离线模式缺少源码或 Cargo 依赖时不会联网补齐。目标依赖使用专用目录，不要求安装宿主 libcap 或借用 Homebrew 目标库。源码归档的 SHA-256 校验不等同于额外做了发布者 PGP 签名验证。

## 在 Mac 上制作候选包

在仓库根目录执行，路径可按自己外置盘的实际位置修改。输出目录必须全新，便于保留每次失败和成功记录。

```sh
export RUSTUP_HOME="/Volumes/MacSSD/dev/rust/rustup"
export CARGO_HOME="/Volumes/MacSSD/dev/rust/cargo"
export PATH="/opt/homebrew/opt/rustup/bin:$CARGO_HOME/bin:$PATH"
export CARGO_BUILD_JOBS=2
export PYTHONDONTWRITEBYTECODE=1
export OHOS_NDK_HOME="/Volumes/MacSSD/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/native"
export HARMONY_JAVA="/opt/homebrew/opt/openjdk@17/bin/java"
export HARMONY_BATCH="$PWD/.harmony-build/候选-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$HARMONY_BATCH/临时目录"
export TMPDIR="$HARMONY_BATCH/临时目录"

python3 scripts/build_harmony_distribution.py helpers \
  --sdk "$OHOS_NDK_HOME" --java "$HARMONY_JAVA" \
  --source-cache "$PWD/.harmony-build/源包缓存" \
  --output-dir "$HARMONY_BATCH/原生资源"

python3 scripts/build_harmony_distribution.py package \
  --sdk "$OHOS_NDK_HOME" --java "$HARMONY_JAVA" \
  --runtime-base /data/storage/el2/base/files \
  --helpers-dir "$HARMONY_BATCH/原生资源" \
  --output-dir "$HARMONY_BATCH/发布产物"
```

`--runtime-base` 必须显式提供，按 OHOS 路径字节数检查完整 socket 地址预算，不在 Mac 上解析此目录。上例是本轮唯一实验性候选，没有真机可用性保证；生产代码逐级检查祖先和私有叶目录，失败时拒绝，不回退 HOME 或运行时环境。更换这个编译契约需要重新审查迁移与沙箱遮蔽，不能同时运行使用不同根的版本。详见[目录权限修复计划](鸿蒙七版目录权限阻塞分析与修复计划.md)。

依赖缓存完整后可以给两个命令加 `--offline`。`package` 的可选 `--build-dir` 指向独立构建缓存目录；正式报告应记录是否复用过缓存。默认会在本批输出目录中创建编译缓存和临时目录。构建记录包含提交、工作区补丁摘要、新增文件摘要及运行目录契约；构建过程中源码变化会阻止打包，应在提交并冻结源码后制作交付包。

两个命令都不执行 OHOS 产物，也不读取或测试登录。签名使用 SDK 的本地自签名模式，不需要在这个流程里输入个人 API Key、申请应用包证书或上传私钥。本次路线依据[华为关于编译与自签名外部程序的说明](https://consumer.huawei.com/cn/support/content/zh-cn16078461/)。商业设备是否接受这种签名还受系统版本、设置及执行身份影响，不能据此宣称所有鸿蒙 PC 均可运行。

## 安装和直接运行 codex

先核对外部 `交付摘要.json` 中的归档 SHA-256，再将归档解压到新目录。进入包目录后执行：

```sh
sh 安装.sh --prefix "$HOME/应用工具/鸿蒙Codex-候选版本"
. "$HOME/应用工具/鸿蒙Codex-候选版本/环境.sh"
command -v codex
codex --version
codex --help
codex doctor --capabilities
```

后三个程序运行命令必须在鸿蒙 PC 执行，Mac 上的安装测试只模拟文件复制与 PATH 配置。安装脚本不执行它们，也不修改 `.zshrc`。需要持续生效时，将上面加载 `环境.sh` 的一行添加到自己的 `.zshrc`，保留原有内容；再次打开终端应能直接输入 `codex`。

安装脚本先验证清单路径和源包摘要，仅复制清单内的普通文件到全新目录，再检查安装后的摘要和执行权限。清单中的符号链接、经过链接的父目录、越界路径和保留文件名会被拒绝；额外文件不会被复制，环境脚本以不覆盖模式新建。它支持空格、中文和单引号路径，拒绝换行及 PATH 分隔符冒号；已有文件、目录或符号链接不会覆盖。发生复制失败时保留目录供排查，不自动清理不确定的路径。安装前后都不访问 Codex 凭据或用户配置。

认证和项目配置继续按[安装配置与运行指南](安装配置与运行指南.md)处理；本轮不执行该指南中的登录测试。`doctor --capabilities` 只列出构建能力策略和工具路径约定，不代表已通过沙箱、剪贴板或网络运行探测。

- [交叉工具链](../../scripts/build_harmony.py)：C/C++、归档、Rust、临时目录及目标依赖隔离。

- [完整流水线](../../scripts/build_harmony_distribution.py)：顺序、摘要、安装包和记录。
- [回归测试](../../scripts/test_harmony_distribution.py)：包布局、平台混入、损坏输入、路径转义和兼容函数。

后续合并上游时，除 Rust 与 Cargo 锁外，还要复核包布局、默认功能、模型工具模式、辅助程序来源以及签名后摘要顺序。更换 SDK 或任一原生程序后都应重新构建并留下新批次，不能沿用旧包的“通过”标签。
