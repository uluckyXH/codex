# 平台识别与系统接口适配

状态：设计稿。覆盖适配01—03，基线见[文档导航](文档导航.md)。

## 现状与目标

候选 Rust 目标为 `aarch64-unknown-linux-ohos`。与仓库工具链一致的 Rust 1.95.0 中，该目标继承 `target_os = "linux"`、Unix 家族，并设置 `target_env = "ohos"`。因此 Linux 条件分支会被选中，需要逐项审核，不能仅新增一个构建目标名称。[OHOS 目标源码](https://raw.githubusercontent.com/rust-lang/rust/1.95.0/compiler/rustc_target/src/spec/base/linux_ohos.rs)、[Linux 基础目标源码](https://raw.githubusercontent.com/rust-lang/rust/1.95.0/compiler/rustc_target/src/spec/base/linux.rs)

该目标描述 OpenHarmony 工具链；能否用于所选商业鸿蒙 PC，由 SDK、ABI、加载器及实际系统能力共同决定。目标名称中的 linux 不表示本项目使用 Linux 子系统。

## 拟议源码分界

在现有模块中拆分确有差异的实现，保留可复用的 Unix 代码。不要整体复制 CLI，也不要批量替换所有 Linux 条件。

```rust
// 设计示意；尚未创建这些平台模块。
#[cfg(target_env = "ohos")]
mod harmony;

#[cfg(all(target_os = "linux", not(target_env = "ohos")))]
mod linux;
```

Cargo 条件依赖、`build.rs` 和运行时平台枚举需同步审核。`cfg!` 产生布尔值，并不能像 `#[cfg]` 一样从编译中移除分支；若分支引用目标不支持的 API，应做真正的条件编译。

## 启动前加固

[进程加固模块](../../codex-rs/process-hardening/src/lib.rs)提供关闭转储、限制调试并移除部分动态加载环境变量的入口。Linux 路径调用 `prctl(PR_SET_DUMPABLE)`，失败可能直接退出，所以它属于启动阻断排查项。

本轮只读审查发现：当前[主 CLI 入口](../../codex-rs/cli/src/main.rs)和[参数分派](../../codex-rs/arg0/src/lib.rs)没有调用 `pre_main_hardening()`。因此加固模块可编译、局部测试通过，均不能证明主 CLI 已执行这些保护。接入主程序前需要区分正常启动和进程设置辅助入口，确认环境清理、描述符及重执行顺序；本轮尚未改变该调用关系。

拟议处理：

1. 在所选 SDK 核对符号、参数类型和常量，再验证普通终端用户是否可以调用。
2. 可复用部分保留；目标行为不同则提供 OHOS 实现，记录其保护能力。
3. 区分接口缺失、权限拒绝和运行故障；明确每类失败是否必须阻止启动，不用吞掉全部错误来让程序运行。
4. 保留环境变量清理的安全语义。若原生库定位依赖 `LD_LIBRARY_PATH`，必须与这里的 `LD_*` 清理一起设计，优先使用经验证的加载布局，不能只在安装说明中设置变量。

尚无证据证明这些调用一定在鸿蒙失败，也没有证据证明能够直接复用。

## 自身路径、辅助入口和资源

| 源码入口 | 现有行为 | 拟议处理 |
| --- | --- | --- |
| [arg0](../../codex-rs/arg0/src/lib.rs) | 根据名称和参数分派补丁、执行及沙箱入口，创建临时软链接 | 保留同一签名可执行文件的辅助入口；审核 OHOS 上允许的路径和调用方式 |
| [spawn_helper](../../codex-rs/utils/pty/src/spawn_helper.rs) | 使用 `/proc/self/exe` 和 `/proc/self/cmdline` | 验证可读性与再次执行行为；若需替代，使用可验证的自身绝对路径 |
| [安装上下文](../../codex-rs/install-context/src/lib.rs) | 从可执行文件定位包、资源和宿主程序 | 移动整个包后仍能定位，禁止依赖构建目录 |
| [构建信息](../../codex-rs/build-info/src/lib.rs) | 包含构建目标等诊断信息 | 如实保留 OHOS target 和适配版本，不伪装成已有受支持 Linux 包 |

如果增加独立辅助 ELF，就把它同时加入编译、权限、签名和打包清单。若复用同一 ELF 的不同参数入口，也需验证每条路径，不因主入口成功就跳过。

## 运行能力检测

建议用内部能力结果表达“支持、缺失、检测失败”，覆盖原生进程、PTY、自身重启、文件锁、文件监听、隔离和网络。结果要携带原因；不要根据系统名字直接把所有能力设为支持。

检测应在对应功能初始化时进行，避免启动时执行有副作用的全套探测。仓库已有 [doctor 诊断实现](../../codex-rs/cli/src/doctor.rs)，需要审核其 OHOS 行为；尚未实现统一的鸿蒙运行能力对象。现有诊断命令不等于已具备签名、加载和隔离能力探针。

## 验收

- 无设备可做：条件分支及 Cargo 依赖审核、目标构建、符号检查、包资源定位的宿主单元验证。
- 必须真机做：正常终端启动、加固调用结果、软链接入口、再次执行、包移动后启动。
- 完成标准：每种入口均选择正确实现，出现不支持能力时能明确解释；不会在帮助界面出现前无说明退出。
