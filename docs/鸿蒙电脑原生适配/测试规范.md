# 鸿蒙电脑原生适配测试规范

适用对象：本项目所有实施、复核和集成会话。目标设备是商业鸿蒙 PC；无设备阶段在 macOS 上完成宿主测试和 OHOS 目标构建，不能据此声明真机兼容。

本规范规定如何选测试、执行和留档。[验证方案与兼容性记录](验证方案与兼容性记录.md)定义产品最终验收内容；[测试报告目录](测试报告/报告目录说明.md)保存每批实际结果。测试后必须留下报告，包括失败、中断和因条件不足没有执行的项目。

## 一、证据层级与用例编号

| 编号 | 验证层级 | 可以证明什么 | 不能据此声称什么 |
| --- | --- | --- | --- |
| 文档01 | 文档、配置示例、链接、差异检查 | 说明、命令语法和本地引用一致 | 命令已经执行或产品已经可用 |
| 脚本01 | 构建脚本宿主测试 | 路径、参数转义、SDK 检查及环境隔离逻辑正确 | SDK 产物能在真机运行 |
| 宿主01 | macOS 单元与集成回归 | 本次实际选中并执行的公共逻辑和 Mac 行为正确 | OHOS 专用分支已执行 |
| 宿主02 | macOS CLI 功能回归 | Mac 构建的端到端行为没有出现相应回归 | 鸿蒙的系统接口、签名或权限可用 |
| 交叉01 | OHOS `cargo check` | 目标条件分支、类型及选中的依赖通过检查 | 最终二进制已完成链接 |
| 交叉02 | OHOS `cargo build` / 最小探针 | 指定源码、SDK、目标组合可以编译和链接 | 商业设备可以加载、执行 |
| 交叉03 | OHOS `cargo test --no-run` | 目标测试程序可编译、链接 | 测试用例已经在 OHOS 上通过 |
| 静态01 | ELF、加载器及动态依赖检查 | 实际产物的静态属性有记录，未发现所检查的问题 | 系统上一定存在这些库或允许这些调用 |
| 包装01 | 包清单、资源路径、摘要与安装脚本检查 | 候选包内容完整，安装逻辑满足已检查的条件 | 鸿蒙用户环境中的安装已经通过 |
| 真机01 | 商业鸿蒙 PC 原生验收 | 所记录设备、系统、用户身份下的真实行为 | 所有鸿蒙机型或系统版本均兼容 |

同一层级可以增加后缀，例如 `交叉01-凭据模块`、`交叉01-完整程序`。报告中同时写明包名、功能组合和具体命令，不能只填写编号。

Mac 默认 `cargo test` 不会运行 `target_env = "ohos"` 专用代码。鸿蒙分支要单独交叉检查；与系统无关的策略、错误处理、参数构造等逻辑尽量拆成宿主可以执行的测试。模拟系统返回值的测试必须标记为模拟，不能证明真实系统提供该能力。

## 二、按改动选择必要测试

| 本次改动 | 至少选择 | 何时增加验证 |
| --- | --- | --- |
| 纯文档、报告或说明 | 文档01 | 新增可执行命令时，验证语法并试跑相关的低成本流程；不重跑整套 Rust 测试 |
| 构建脚本、SDK 路径、工具链变量 | 脚本01、交叉02、静态01 | 改到 Cargo / C/C++ 配置时增加受影响包的交叉01 |
| Rust 逻辑或系统接口 | 相关宿主01、交叉01 | 改到外部符号或链接时增加交叉02；改到目标测试时增加交叉03 |
| 依赖、Cargo feature 或条件编译 | 受影响包交叉01、必要的交叉02、相关宿主01 | 进入集成前对最终代码做完整 CLI 目标检查；涉及原生库时检查产物 |
| 进程、PTY、取消和描述符 | 相关宿主01、交叉01、交叉03 | 运行语义必须列入真机01，不能因 Mac 测试通过而取消 |
| 沙箱、权限或签名 | 可执行的逻辑测试及目标构建 | 真机01 中同时包含允许和拒绝用例；未验证前不宣称已隔离或已获系统接受 |
| 配置、认证或状态迁移 | 相关宿主01及交叉01 | 涉及持久化、系统证书或登录交互时增加对应真机用例 |
| 包布局、安装入口或更新路径 | 包装01、相关脚本测试、候选产物检查 | 分发前在干净的鸿蒙用户环境执行真机安装与启动 |
| 多会话集成或上游合并 | 对合并后的代码运行受影响回归和完整交叉01 | 可交付候选还须完整链接、静态与包检查；正式支持声明须具备真机证据 |

在报告里说明选项和未选项的理由。已通过且未受后续修改影响的测试不为凑数量重复执行；修改、失败或新证据造成疑问时，重新运行受影响用例。全文没有“无论改什么都跑全仓”的要求。

## 三、每个会话独立留档

1. 测试前记录执行者及会话标识、工作目录、分支、完整 `HEAD`、与基线相比的变更范围。
2. 工作区有改动时注明“含未提交修改”，保存本次被测文件或补丁摘要，不能只用 `HEAD` 冒充完整测试版本。新增源文件也要纳入摘要。
3. 每批使用独立批次目录和构建输出。共享 Cargo 下载缓存可以由 Cargo 自身协调；不同会话不共享可变的包装器、临时文件或日志目录。
4. 测试期间若其他会话改变了被测代码，保留前后差异并重跑受影响用例。优先使用独立工作目录或 worktree；不要切换其他会话正在使用的共享分支，或清理其构建目录。
5. 合并前各会话交付自己的报告；集成方针对合并结果生成新报告。单个分支通过，不能推导出合并结果通过。

报告编号采用“北京时间日期与时刻—中文任务—会话短标识”。同一目录只代表一批不可混淆的执行；重测生成新目录并链接旧报告，不覆盖原失败证据。模板、目录说明和报告正文均使用中文文件名，技术命令与原有源码标识保留原名。

## 四、准备一批测试

先按[苹果电脑构建环境与外置盘配置](苹果电脑构建环境与外置盘配置.md)确认 Rust、Python 3.11 以上和 SDK。以下从仓库根目录执行，变量只在本次 Shell 使用；任务名和会话标识须替换。

```sh
cd /Volumes/MacSSD/Repositories/codex
export RUSTUP_HOME="/Volumes/MacSSD/dev/rust/rustup"
export CARGO_HOME="/Volumes/MacSSD/dev/rust/cargo"
export PATH="/opt/homebrew/opt/rustup/bin:$CARGO_HOME/bin:$PATH"
export OHOS_NDK_HOME="/Volumes/MacSSD/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/native"

harmony_repo_root="$(git rev-parse --show-toplevel)"
harmony_run_id="$(TZ=Asia/Shanghai date +%Y-%m-%d-%H%M%S)-待填任务-待填会话"
harmony_run_root="$harmony_repo_root/.harmony-build/测试批次/$harmony_run_id"
harmony_report_root="$harmony_repo_root/docs/鸿蒙电脑原生适配/测试报告/$harmony_run_id"
harmony_toolchain="$(python3 -c 'import tomllib; print(tomllib.load(open("codex-rs/rust-toolchain.toml", "rb"))["toolchain"]["channel"])')"

mkdir -p "$harmony_run_root/日志" "$harmony_run_root/临时目录"
# mkdir 不带 -p：已有同名报告时停止复制，改用新批次名。
mkdir "$harmony_report_root" && \
  cp docs/鸿蒙电脑原生适配/测试报告/测试报告模板.md \
     "$harmony_report_root/测试报告.md"
export TMPDIR="$harmony_run_root/临时目录"
```

只有成功创建新报告目录后才继续。不要重新使用已有批次名。报告创建前记录被测工作区状态；报告自身和日志的新增不等于产品源码发生变化。

环境记录至少包含：Rust/Cargo 版本、目标 triple、SDK 版本及 API、Clang、宿主系统与架构、选用的 features/profile、源码状态和外置盘输出位置。真机报告还须记录设备型号、完整系统版本、终端、Shell、普通用户或调试身份、签名工具版本及签名方式。只记录必要环境变量，不保存完整环境、密钥或认证文件。

## 五、保存命令、日志及真实退出码

下面的函数适用于本节的普通短时命令；每次调用使用新用例名。不要把命令拼成字符串交给 `eval`，也不要用没有保留原命令退出码的 `命令 | tee 日志` 判断成功。

```sh
harmony_run_case() {
  harmony_case_name="$1"
  shift
  harmony_case_log="$harmony_run_root/日志/$harmony_case_name.log"
  if [ -e "$harmony_case_log" ]; then
    printf '用例日志已存在，请使用新名称：%s\n' "$harmony_case_log" >&2
    return 125
  fi
  harmony_case_started="$(TZ=Asia/Shanghai date '+%Y-%m-%dT%H:%M:%S%z')"
  if (
    printf '工作目录：%s\n' "$PWD"
    printf '开始时间：%s\n' "$harmony_case_started"
    python3 -c 'import shlex, sys; print("命令：" + shlex.join(sys.argv[1:]))' "$@"
    "$@"
  ) > "$harmony_case_log" 2>&1; then
    harmony_case_exit=0
  else
    harmony_case_exit=$?
  fi
  harmony_case_finished="$(TZ=Asia/Shanghai date '+%Y-%m-%dT%H:%M:%S%z')"
  printf '\n结束时间：%s\n退出码：%s\n' \
    "$harmony_case_finished" "$harmony_case_exit" >> "$harmony_case_log"
  printf '%s\t%s\t%s\t%s\n' "$harmony_case_name" "$harmony_case_started" \
    "$harmony_case_finished" "$harmony_case_exit" >> "$harmony_run_root/执行结果.tsv"
  printf '%s：退出码 %s；日志 %s\n' "$harmony_case_name" "$harmony_case_exit" "$harmony_case_log"
  return "$harmony_case_exit"
}
```

若工具超时、任务取消或 Shell 被强制结束，函数可能来不及写结束记录。保留已产生的日志，报告写“中断，未完成”，记录已知信号或工具状态，不补造退出码 0。下面的调用是按需选择的菜单，不要求顺序全部执行。

### 1. 构建脚本与 Mac 回归

```sh
harmony_run_case 脚本01-构建入口 \
  python3 -m unittest discover -s scripts -p test_build_harmony.py -v

# 明确指定当前 Apple Silicon Mac 目标，避免继承外部的 OHOS 默认目标。
harmony_run_case 宿主01-凭据与进程 \
  env CARGO_TARGET_DIR="$harmony_run_root/宿主产物" \
  rustup run "$harmony_toolchain" cargo test \
  --manifest-path codex-rs/Cargo.toml --locked --target aarch64-apple-darwin \
  -p codex-keyring-store -p codex-utils-pty
```

Intel Mac 使用实际宿主目标；其他模块替换为本次受影响的包。报告分别记录通过、失败、忽略、过滤的数量；0 项测试退出 0 不等于功能已覆盖。Mac CLI 端到端测试要注明实际执行的是 Mac 产物。

### 2. OHOS 检查、探针与完整候选构建

```sh
harmony_run_case 交叉01-凭据与进程 \
  python3 scripts/build_harmony.py check --sdk "$OHOS_NDK_HOME" \
  --output-dir "$harmony_run_root/鸿蒙构建" \
  --package codex-keyring-store --package codex-utils-pty

harmony_run_case 交叉01-网络模块 \
  python3 scripts/build_harmony.py check --sdk "$OHOS_NDK_HOME" \
  --output-dir "$harmony_run_root/鸿蒙构建" --package codex-http-client

harmony_run_case 交叉02-最小探针 \
  python3 scripts/build_harmony.py probe --sdk "$OHOS_NDK_HOME" \
  --output-dir "$harmony_run_root/鸿蒙构建"

# 完整检查可能在已登记的依赖问题处失败，仍须保存报告。
harmony_run_case 交叉01-完整程序 \
  python3 scripts/build_harmony.py check --sdk "$OHOS_NDK_HOME" \
  --output-dir "$harmony_run_root/鸿蒙构建"

# 在依赖收敛后选用；输出成功才能登记完整 CLI 候选产物。
harmony_run_case 交叉02-完整程序 \
  python3 scripts/build_harmony.py build --release --sdk "$OHOS_NDK_HOME" \
  --output-dir "$harmony_run_root/鸿蒙构建"
```

`probe` 同时输出 ELF 静态信息，但还需要检查输出内容。报告中将“链接成功”和“静态属性已复核”分开填写。不要在 Mac 上尝试直接执行 OHOS ELF，也不要通过伪造内置 `cfg` 把 Mac 标成鸿蒙。

### 3. 目标测试程序交叉链接

当前构建入口没有 `test` 子命令。可复用其环境配置，只构建测试程序，不启动目标程序：

```sh
harmony_run_case 交叉03-测试程序 \
  python3 - "$OHOS_NDK_HOME" "$harmony_run_root/鸿蒙构建" <<'PY'
import os
from pathlib import Path
import sys
sys.path.insert(0, "scripts")
from build_harmony import REPO_ROOT, TARGET, TOOLCHAIN, build_environment, native_sdk, run
sdk = native_sdk(Path(sys.argv[1]))
output = Path(sys.argv[2]).resolve()
env = build_environment(sdk, output, dict(os.environ))
env["RUSTUP_AUTO_INSTALL"] = "0"
run(["rustup", "run", TOOLCHAIN, "cargo", "test", "--locked", "--no-run",
     "--target", TARGET, "-p", "codex-keyring-store", "-p", "codex-utils-pty"], env)
PY
```

使用脚本文件或标准输入承载测试内容时，报告须附脚本内容或被测提交中的源码路径及摘要；日志中的 `python3 -` 本身不足以复现。不得把 `--no-run` 的结果写成“鸿蒙测试全部通过”。

### 4. 静态、包和设备验收

静态检查使用所选 SDK 的 `llvm-readelf`、`llvm-nm` 等工具，记录文件摘要、架构、解释器、动态依赖、RPATH/RUNPATH 和必要符号。动态程序允许存在待加载器解析的导入符号，应检查它们是否由预期目标库提供，不能把所有未定义导入都判为链接错误。

包检查覆盖主程序、辅助 ELF、动态库、资源、文件权限、相对定位、许可和签名前后摘要。Mac 上模拟解包或 PATH 配置仅说明该测试环境的脚本行为。签名材料和认证数据不进入报告。

真机阶段按[验收表](验证方案与兼容性记录.md)逐项执行，包含启动、登录、中文项目读写、命令执行、PTY、取消、恢复，以及越权写入和禁止联网的拒绝用例。商业鸿蒙 PC 普通用户终端是最终入口；调试器、手机、平板或模拟器的补充结果另行标明。

### 5. 认证专项

账号登录与 API Key 都是必须保留的适配能力；设计和源码入口见[网络登录与凭据适配](网络登录与凭据适配.md)。以下是后续执行清单，当前不是通过记录。每个编号同时标记宿主模拟、目标检查或真机实测层级。

| 用例编号 | 验证内容 | 通过条件与边界 |
| --- | --- | --- |
| 认证01-密钥输入与存储 | 标准输入接收、空输入、文件不可写、新进程读取 | 有效输入按上游规则保存；失败不能显示成功；此项不证明服务端接受 Key |
| 认证02-官方密钥请求 | 有效、无效或撤销 Key，权限不足、额度及网络错误 | 实际模型请求和流式响应有证据；保留服务端拒绝，不能只检查 `login status` |
| 认证03-设备授权 | 代码显示、批准、轮询、取消、过期、账号未启用 | 各状态正确；模拟结果和真账号结果分开；拒绝时不自行更换认证方式 |
| 认证04-浏览器回调 | 自动唤起失败、同机手动链接、回环端口、state/PKCE | 手动与自动入口分别记录；错误回调被拒绝；Mac 回环成功不代表鸿蒙成功 |
| 认证05-凭据生命周期 | ChatGPT 刷新、刷新失败、退出、API Key 替换 | 重开终端读取有效状态；退出清除对应本地凭据；API Key 不套用 token 刷新规则 |
| 认证06-存储与管理限制 | 文件权限、并发、强制 keyring、强制登录方式和工作区 | 不绕过管理限制；OHOS 未实现的 keyring 明确失败，不伪装持久保存 |
| 认证07-自定义服务 | `base_url`、`env_key`、认证选择、流式与工具调用 | 请求发往预期服务且使用预期凭据；环境变量缺失或协议不兼容有明确错误 |
| 认证08-升级与诊断 | 旧认证格式、新旧配置、退出后的环境凭据、日志检查 | 保留兼容性与上游选择规则；日志不含完整密钥、设备码、授权链接和回调参数 |

优先复用 `codex-login` 现有的状态机、存储、回调、刷新及退出测试；相关 CLI 和提供方改动另选对应测试。使用专用临时用户数据目录和模拟凭据，不能读写执行会话本人的认证缓存。纯文档变更只执行文档检查，不为本清单发起真实登录或模型请求。

实际服务验收使用执行者明确提供的测试账号或密钥，并记录服务、模型、结果及必要错误码；不把密钥值写入命令日志。API Key 与 ChatGPT 路径分别保存结果，未执行的方式不得借另一方式的成功标成通过。`codex logout` 后若环境仍提供凭据，应按上游选择规则解释，不能误报本地缓存未清除。

## 六、状态与结论规则

| 状态 | 使用条件 |
| --- | --- |
| 通过 | 真实执行完成，退出结果及本用例断言符合预期，证据可定位 |
| 失败 | 命令或断言实际失败；已知的编译错误仍属于失败，不因“预期会失败”改成通过 |
| 阻塞 | 用例未能开始，或后续步骤无法继续，例如无 SDK、无设备或前置构建失败；注明原因和所需条件 |
| 未执行 | 本轮没有执行，包括中断而未完成的用例；说明选择或中断原因 |
| 不适用 | 用例不属于本次改动/声明范围，给出具体理由；无设备不能作为真机验收永久不适用的理由 |

专门测试失败处理时，预先约定的非零退出码可以作为测试断言；例如验证日志函数能保留退出码 7。必须明确这是测试工具用例，不把实际构建失败包装成成功。

报告分别给出“本次改动验证结论”“完整 CLI 构建状态”“商业鸿蒙 PC 验证状态”。不得用一个绿色“全部通过”合并三个层级。无设备时最多达到“相应宿主检查和目标构建通过，真机待验证”；完整候选还须有实际完整链接及包检查证据。

## 七、报告完成与交付

每次执行后填写[测试报告模板](测试报告/测试报告模板.md)，包括测试范围、源码身份、环境、命令、时间、退出码、测试数量、结果、证据、未执行项和下一步。修复后新建重测报告，并引用原失败报告。

报告和必要的脱敏证据进入 Git；原始日志、编译缓存、可执行文件及大附件保留在外置盘 `.harmony-build/测试批次/<批次名>`。提交前检查附件内容，只纳入本轮报告相关文件。报告应保存足够的命令和关键输出，使换电脑的会话不依赖原机器的缓存才能理解结论。

将报告链接登记到[报告目录说明](测试报告/报告目录说明.md)；集成会话合并各自独立目录，统一更新索引。后续适配、维护或交付说明引用具体报告和被测版本，不引用含糊的“之前测试过”。
