# 安装配置与运行指南

状态：原生候选包与安装脚本已生成，Mac 上文件复制、摘要、权限和 PATH 模拟通过；尚未在鸿蒙 PC 执行。下列设备操作需在实际型号和系统上验收，不能据此宣布正式支持。

## 使用前应具备什么

| 条件 | 说明 |
| --- | --- |
| 商业鸿蒙 PC | 型号、CPU、系统版本在包的兼容性清单中 |
| 原生终端 | 按该系统的官方说明开启和使用 |
| 系统运行设置 | 按官方指引允许已签名的外部扩展程序运行 |
| 鸿蒙原生包 | 主程序、rg、资源及必要辅助程序齐全，不能使用普通 Linux 包代替 |
| 认证与网络 | 可使用的账号登录方式或 API Key，以及到所选服务的网络连接 |
| 本地开发命令 | 所需 Git、Shell、项目工具链具有实际可用的鸿蒙原生版本 |

运行 Codex 本身无需 Node.js 包装器或完整 Rust 编译环境。项目本身需要 Node.js、Rust 或其他运行时的，按该项目另行准备。收到已经正确签名的包时，不应要求用户为了日常启动而保留 hdc 调试连接。

官方依据：[原生终端](https://consumer.huawei.com/cn/support/content/zh-cn16052280/)、[外部扩展程序](https://consumer.huawei.com/cn/support/content/zh-cn16079826/)。不同系统版本的设置和签名接受条件以实际兼容性记录为准。

## 第一步：取得并检查完整包

本轮候选归档、源码版本与 SHA-256 见[实施记录](实施进展与构建记录.md)，文件在 Mac 外置盘上。尚无公开下载渠道或应用更新器；包内安装说明和构建记录明确标记“未真机验证”。

先核对完整包摘要与来源，再解压；保留目录结构，不单独拷贝 `bin/codex`。签名方式及所有原生文件记录见包内“构建与签名记录.json”。自签名和证书流程参见[打包与签名](构建打包与签名设计.md)。

如果拿到的是未签名开发产物，应先由开发流程完成签名和基本加载检查；它还不是正式可安装版本。不能仅添加可执行权限来代替签名。

## 第二步：放置程序目录

在解压后的“鸿蒙Codex”目录，运行随包安装器，将 `--prefix` 指定为已确认可写且允许执行的全新目录：

```sh
sh 安装.sh --prefix "$HOME/应用工具/鸿蒙Codex"
```

安装器先校验清单，只复制列出的普通文件，拒绝清单路径中的符号链接或越界。已有安装目录不会覆盖；额外文件不会被复制，也不会跟随额外的 `环境.sh` 链接写入外部文件。整个过程只处理文件，不执行 Codex 或读取其认证配置。安装后的结构为：

```text
~/应用工具/鸿蒙Codex/
├── bin/codex
├── codex-path/rg
├── codex-resources/bwrap
├── codex-package.json
├── 文件校验清单.sha256
└── 环境.sh
```

该目录是待验证的用户目录约定，不是鸿蒙所有版本强制路径。若目标系统使用其他可执行目录，替换下文全部安装路径。

安装器会创建父目录，并在复制前后检查摘要和可执行位。终端需提供 `sh`、基本文件工具以及 `sha256sum` 或 `shasum`。这些工具在具体鸿蒙 PC 上的可用性仍需确认。

若已有同名安装目录，停止覆盖并保留旧包；用户端升级流程另行设计。不要把新程序包复制到 `.codex` 用户数据目录中。

## 第三步：让终端找到 codex

先按安装器输出在当前终端加载环境，再确认程序可运行：

```sh
. "$HOME/应用工具/鸿蒙Codex/环境.sh"
```

```sh
"$HOME/应用工具/鸿蒙Codex/bin/codex" --version
"$HOME/应用工具/鸿蒙Codex/bin/codex" --help
```

若失败，先处理文末的加载错误；修改 PATH 无法解决签名、架构或缺库问题。

华为环境说明使用用户 `~/.zshrc`。用可用的文本编辑器在该文件中添加下列一行，已有相同配置时不要重复添加，也不要覆盖原文件：[官方环境说明](https://consumer.huawei.com/cn/support/content/zh-cn16089085/)

```sh
. "$HOME/应用工具/鸿蒙Codex/环境.sh"
```

重新打开终端后验证：

```sh
command -v codex
codex --version
codex doctor --capabilities
```

`doctor --capabilities` 输出构建能力清单，不加载 Codex 配置或认证，不发模型请求，也不代表已经探测到设备权限。CLI 通用启动流程仍会初始化 dotenv。

`command -v` 应指向刚放置的鸿蒙程序。若指向别的安装、别名或函数，先检查原有配置并解决名称冲突。包内 rg 应由经过适配的资源定位逻辑找到，不要求用户手动修改系统级 PATH。

## 第四步：配置用户目录和首轮能力

下文按默认 `~/.codex` 编写。已有自定义 CODEX_HOME 时，使用已有的实际目录，不创建两套配置，也不在安装时改写 HOME。

首次使用、目录不存在时可创建：

```sh
mkdir -p "$HOME/.codex"
chmod 700 "$HOME/.codex"
```

编辑 `~/.codex/config.toml`，合并必要配置，不覆盖用户已有文件。候选首版配置如下，最终应由实际发布能力确认：

```toml
cli_auth_credentials_store = "file"
mcp_oauth_credentials_store = "file"
approval_policy = "untrusted"
sandbox_mode = "read-only"
check_for_update_on_startup = false

[features]
code_mode = false
code_mode_only = false
code_mode_host = false
code_mode_prewarm = false
shell_zsh_fork = false
daemon_auto_start = false
```

本轮已在源码默认值、配置入口和工具策略中约束缺少后端的能力；上述显式配置便于阅读和迁移。配置不能创造目标系统缺失的沙箱能力。配置解释及更新入口限制见[配置专题](配置与功能开关适配.md)。

不要把 API Key、证书私钥或个人项目内容写进随包配置示例；模型名称按账号和实际服务选择，本方案不硬编码一个可能无权限的模型。

## 第五步：登录

以下是后续用户操作说明。本轮按要求未执行真实或模拟登录、凭据读写测试或模型请求。账号登录与 API Key 是需要长期保留的独立入口。以下按个人选择和账号允许的方式择一执行，不要求依次运行全部登录命令；重新登录可能替换已有凭据。

账号允许设备授权时，在鸿蒙终端执行：

```sh
codex login --device-auth
```

按终端显示的地址和代码完成认证。浏览器可以只负责授权，Codex 和本机项目操作始终在鸿蒙 PC 上执行。账号不支持设备授权时，选择其他受支持登录方式，不能把服务端拒绝当成移植问题。

使用 API Key 且已通过自己的安全方式设置 `OPENAI_API_KEY` 时，可从标准输入登录：

```sh
printenv OPENAI_API_KEY | codex login --with-api-key
```

不要把实际密钥直接写进命令参数、示例文档或项目配置。随后检查：

```sh
codex login status
```

API Key 的保存成功和 `login status` 输出正常，不证明服务端已接受密钥。还需在第六步完成一次实际模型请求；Key 的权限、撤销状态及额度由服务端判断。API Key 使用自己的 API 计费和权限，不消耗 ChatGPT 订阅内的使用额度。[官方认证说明](https://learn.chatgpt.com/docs/auth)

使用普通浏览器登录时，现有入口为：

```sh
codex login
```

若未自动打开浏览器，在同一鸿蒙 PC 的浏览器打开终端显示的链接。该方式需要本机回调可用；另一台设备协助授权应选择设备码流程。浏览器唤起和回调仍待鸿蒙真机验证。

需要清除本地保存的认证时，现有命令为：

```sh
codex logout
```

登出不等于从 OpenAI 平台撤销 API Key，也不会删除用户自己在外部环境或密钥管理工具中设置的密钥。使用自定义模型服务时，按[认证专题](网络登录与凭据适配.md#api-key-与自定义服务接入)配置该服务的地址和 `env_key`，不默认把服务 Key 当作官方 Key 登录。

命令依据当前[登录源码](../../codex-rs/cli/src/login.rs)。凭据保存和 ChatGPT token 刷新尚待另行安排目标系统验证；鸿蒙文件存储尚不能宣称等同于系统加密密钥库。

## 第六步：进入项目并启动

进入一个已经存在、具有访问权限的本机测试项目：

```sh
cd "$HOME/代码/鸿蒙验收项目"
codex
```

示例项目路径需替换成真实目录。首次先验证普通问答、读取文件和列出项目结构；按界面要求处理项目信任与操作审批。

在该版本已经通过工作区隔离验收后，若要执行正常代码修改，将用户配置中现有的 `sandbox_mode` 改为 `"workspace-write"`，保留审批设置。不要另加第二个重复键，也不要在缺少后端支持时靠扩大权限绕过失败。

完成一次“读取文件 → 修改一处内容 → 执行原生测试命令 → 查看差异 → 取消长任务 → 恢复会话”的验收。以后进入已配置的项目目录，直接执行 `codex` 即可使用；无需每次重配 PATH 或重新签名未变化的安装文件。

在同一测试项目退出后，可验证最近会话恢复：

```sh
codex resume --last
```

## 运行时需要记住的边界

Codex 可运行并不表示任意 Linux 命令都已移植。项目测试程序如生成新的可执行文件，需要遵循鸿蒙的签名规则；由对应工具链处理，不修改已经签名的 Codex 程序。

用户配置、认证和会话留在用户目录。后续替换程序时应保留它们，但具体更新和回退方式本轮不设计。

当前 OHOS 源码已阻止 TUI、CLI 及后台服务调用不兼容的上游更新器。后台服务包安装也会明确拒绝将 OHOS 当作 Linux musl；`codex app-server daemon` 的安装和更新不在首批已完成能力中。后续发布的鸿蒙包应按其专用说明手动安装，不使用上游 Linux 包覆盖。

## 常见问题的排查顺序

| 现象 | 先检查什么 |
| --- | --- |
| 找不到 codex | 安装路径、`.zshrc` 是否加载、PATH 和名称冲突 |
| 文件存在但拒绝执行 | 签名方式、外部扩展设置、执行权限和所在目录 |
| 格式错误或找不到动态库 | CPU、目标 ABI、加载器和完整资源包；不要再下载普通 Linux 包替换 |
| 版本帮助可用，启动即退出 | 启动加固、配置、资源定位及完整错误信息 |
| 不能登录或模型请求失败 | 账号方式、DNS、时钟、代理、TLS 根证书和凭据权限 |
| 能聊天但不能执行命令 | Shell、子进程、辅助文件和隔离能力 |
| 能运行命令但无法执行新编译的程序 | 项目工具链、目标 ABI 和新产物签名 |
| 中文或粘贴异常 | 终端版本、输入法和已声明的 TUI 支持范围 |
| 保存或恢复失败 | 用户目录、授权、空间、文件锁和数据库错误 |

反馈材料保留源码/适配版本、设备系统、失败命令与脱敏错误。不要提交 `auth.json`、token 或整个真实会话目录。
