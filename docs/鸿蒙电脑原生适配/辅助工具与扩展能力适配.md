# 辅助工具与扩展能力适配

状态：覆盖适配19—22。原生 rg、bwrap 和静态 libcap 已构建，辅助程序已签名并组包；Git 作为外部原生工具准备，V8、定制 zsh、语音及桌面自动化暂缺后端并受源码约束。见[实际进展](实施进展与构建记录.md)。

## 原生 Git 和搜索

优先验证设备提供或可官方安装的原生工具，再决定是否自行移植随包交付。Git 不得假定预装；需要检查 `status`、`diff`、补丁、工作树、忽略规则、中文文件名和权限。涉及网络操作时还需验证 Git 自己的 TLS、SSH 或凭据支持，它们不由 Codex 登录自动提供。

既有打包器从 DotSlash 清单获取 rg。OHOS 要有自己的构建与校验来源，禁止把 `linux-aarch64` 条目直接复用为鸿蒙条目。记录版本、源代码或官方来源、许可、摘要和签名结果。

区分内置 Rust 搜索逻辑与模型通过 Shell 调用 rg；两条路径都需检查。缺少 Git 或 rg 时，诊断应指出实际缺失项及受影响功能。

## 项目开发工具链

Codex 负责启动本机命令，不会自动让所有项目工具兼容鸿蒙。最终指南应列出已经验证的 Shell、Git、编译器及测试工具；Node.js、Python、Rust 等按实际原生版本另行登记。

用户项目构建生成的 ELF/.so 可能同样需要签名。首个验收项目需提供明确的构建、签名与执行步骤，且不依赖未声明运行时。首版不能声称任意 npm、Python 包或 Linux 开发工具都能直接执行。

## MCP、插件与技能

本地 MCP 最小验证应覆盖原生子进程启动、参数和环境、JSON 消息、并发请求、超时、取消、关闭和子进程回收。记录运行时版本，不依赖 `/usr/bin/node` 等未经确认路径。

MCP 子进程应采用与普通本地工具一致的权限设计。OAuth 的 token 存储与 Linux keyring 依赖按[网络专题](网络登录与凭据适配.md)处理。

插件下载后包含脚本或 ELF 时，应检查其运行需求和系统接受条件。文本技能可复用不等于技能调用的全部工具已经适配。对暂不支持的能力给出明确原因，不替换成远程执行服务来满足原生验收。

## V8 和定制 Shell 的两条选择

**首轮裁剪：** 同步调整 Cargo 依赖、功能注册、默认配置、宿主预热和打包清单；确认普通工具调用路径仍可用。模型配置或上游逻辑若强制依赖该能力，需要先解决该依赖，不能靠隐藏开关完成裁剪。

**保留能力：** 按[仓库 V8 构建说明](../../third_party/v8/README.md)准备目标库与对应绑定，验证可执行内存、内存映射、线程和宿主协议；宿主 ELF 也要签名。现有预编译发布组合未提供 OHOS，不能下载其他平台的库混用。

现有[打包器说明](../../scripts/codex_package/README.md)要求完整包携带 `codex-code-mode-host`，因此裁剪必须修改打包输入和校验逻辑。单独构建 `codex-cli` 是否引入 V8 以实际依赖图为准，不能把完整包需求直接等同于每次 CLI 编译需求。

## 本地服务与后台能力

CLI 直接依赖 app-server、daemon 和 UDS 相关组件，所以不能因为首版只用终端就跳过它们的编译路径。运行层面则将按需本地辅助进程与长期后台服务分开登记。

首版无需增加开机自启动或图形 App；如启用 daemon，必须另行验证启动、停止、套接字权限、PID 身份、日志和异常清理，并阻止其更新循环获取不匹配的上游产物。

## 完成标准

包内每个工具都有匹配架构、依赖来源、签名和能力记录。首版暂缓功能在编译、注册、配置与包内容上保持一致。支持矩阵细到具体功能与运行时，不能只填写“插件兼容”或“Git 支持”。
