# 验证方案与兼容性记录

状态：设计稿。覆盖适配29—30，统筹所有专题的验证。用户目前没有可直接验证的鸿蒙 PC，以下没有任何真机通过记录。

所有会话的执行步骤、证据级别和报告要求统一按[测试规范](测试规范.md)落实；实际结果存入[测试报告目录](测试报告/报告目录说明.md)。本文维护产品验收范围，不作为一次测试已经完成的证明。

## 证据层级

| 层级 | 可以做什么 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 源码与文档检查 | 条件分支、配置、依赖声明、包布局及接口设计审核 | 已发现的问题和计划覆盖范围 | 实际构建、加载与运行 |
| 宿主测试 | 纯逻辑、策略转换、配置合成、数据格式及打包检查 | 修改后公共逻辑的行为 | 鸿蒙内核、终端或签名机制 |
| 目标构建与静态检查 | OHOS 编译、链接、ELF、符号和动态依赖 | 指定工具链产物可生成且静态属性符合预期 | 商业设备是否接受或正确执行 |
| 签名候选包 | 签名信息检查、文件清单及归档完整性 | 产物已完成所选签名步骤 | 真机验证通过或跨设备兼容 |
| 商业鸿蒙真机 | 普通用户终端启动、工具调用、隔离及安装 | 所记录设备与系统基线的实际行为 | 未测型号和其他系统版本 |

在宿主执行 `cargo test`，或把 Linux runner、开发板、模拟器结果作为补充，都不得替代商业鸿蒙 PC 的最终验收。

## 无设备阶段的工作

先完成与实际改动相关的目标构建和必要测试，不要求为了文档或可逆的小改动增写重复测试。检查包中每个 ELF 的目标、动态依赖及签名清单，确认不存在构建机绝对路径或错误平台下载。

目标集成测试如不能运行，明确记录“未执行”；可以分别验证测试程序能够编译，但不能写成测试已通过。没有安装 SDK 时，也不能把 Rust 官方存在该目标写成“本项目交叉编译通过”。

## 真机最小探针

已经提供[最小 Rust 探针](../../scripts/harmony_probe.rs)，可交叉链接成 ARM64 ELF，输出基本启动信息、当前目录和自身路径；尚未签名或在真机执行。它不改全局设置。后续扩展独立的能力探针，先于完整 CLI 功能验收执行，文件和进程测试限定在专用测试目录。

探针内容：启动与退出、线程、时间、随机数、文件读写和锁、DNS/TLS、管道、子进程、PTY、信号、Unix 套接字、自身再次执行及候选隔离机制。各能力独立报告，避免一项失败隐藏其他结果。

普通终端、hdc 调试身份若结果不同，分别记录；验收以最终用户实际入口为准。

## 一次完整编码任务

登录细分用例按[测试规范的认证专项](测试规范.md#5-认证专项)执行。不能用“设备码或 API Key 任一通过”覆盖另一路结果，也不能把 API Key 本地保存或状态查询视为实际模型请求已经成功。

使用专门的测试仓库和已声明的原生开发工具：读取说明、查看一个文件、修改一处逻辑、执行测试、查看 Git 差异、取消一个长任务，再退出并恢复会话。

如果所用测试会生成 ELF，加入明确的项目产物签名步骤。任务完成后检查输出、文件内容、退出码及是否有残留进程；只完成聊天或 `--help` 不算编码闭环。

## 诊断交付

计划让诊断信息包含源码版本、适配版本、目标、安装路径、Shell、关键能力和缺失辅助程序。优先扩展既有日志与构建信息，是否增加新的命令另行决定；当前不提供不存在的诊断命令给用户执行。

日志保留失败阶段、错误码和脱敏上下文。移除凭据、认证文件内容、私钥和无关项目内容。失败应能归因到构建、加载、签名、系统接口、配置、网络或账户，不统一打印“运行失败”。
