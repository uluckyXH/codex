# 鸿蒙沙箱能力与执行方式分析

核对日期：2026-10-03。源码基线：`abeb98f47`，商业鸿蒙 PC 7.0 真机报告版本：`0.160.0-dev.harmony.g913098105a40`。

## 结论

Codex 并非所有操作都必须通过自身沙箱。命令执行和文件读写都有不经 Codex 沙箱的路径。但用户选择受限权限时，程序必须先建立对应隔离，不能在失败后悄悄放开权限。

现有证据还不能判定“鸿蒙 PC 不支持 bubblewrap 沙箱”。本次错误发生在 Codex 准备挂载参数的校验阶段，早于真正执行 bubblewrap 的隔离预检。包内 `bwrap --version` 成功仅说明程序能启动，不代表命名空间、挂载和系统调用过滤可用。

## 两层不同的隔离

| 层次 | 谁建立 | 对本项目意味着什么 |
| --- | --- | --- |
| 鸿蒙应用隔离与访问控制 | 操作系统、应用启动和权限机制 | Codex 从 HiShell 启动后，仍受所在进程身份和系统策略约束 |
| Codex 工具受限执行 | 本分支采用的 bubblewrap、进程加固及过滤代码 | 需要操作系统允许该进程进一步建立所需隔离；已有应用沙盒不能自动等价替代 |

华为《HarmonyOS NEXT 安全技术白皮书》5.3 节说明应用独立沙盒、强制访问控制和系统调用过滤。该文档为 2024 年版本，可以确认机制上的区分，不能证明 PC 7.0 的 HiShell 对具体系统调用开放了什么权限。[华为官方白皮书](https://consumer.huawei.com/content/dam/huawei-cbg-site/cn/mkt/privacy/privary-new/250610/down/HarmonyOS%20NEXT%E5%AE%89%E5%85%A8%E6%8A%80%E6%9C%AF%E7%99%BD%E7%9A%AE%E4%B9%A6.pdf)

OpenAI 官方说明 Linux 的打包 bubblewrap 需要非特权用户命名空间能力；同时说明沙箱与人工批准是两个不同控制，`danger-full-access` 模式不施加 Codex 的文件系统和网络沙箱边界。[Codex 官方说明](https://learn.chatgpt.com/docs/sandboxing)

截至本次核查，未找到华为官方承诺“商业 PC 7.0 的 HiShell 普通子进程可创建 bubblewrap 所需全部隔离”的资料，也没有找到足以断言“一律不支持”的官方依据。OpenHarmony 开源实现、Rust OHOS target、SDK 中有某个函数声明，都不能单独替代这台商业设备的运行验证。

## 本地源码依据

- [沙箱选择](../../codex-rs/sandboxing/src/manager.rs)：`select_initial` 在策略不需要隔离时返回 `SandboxType::None`；`transform` 对该类型保留原命令参数，不包裹沙箱执行器。
- [策略判断](../../codex-rs/sandboxing/src/policy_transforms.rs)：`should_require_platform_sandbox` 综合文件、网络及受管网络要求判断。不能仅把一个文件权限选项改宽，就推断所有调用都不会要求隔离。
- [文件操作路由](../../codex-rs/exec-server/src/local_file_system.rs)：`file_system_for_reads` / `file_system_for_writes` 根据上下文选择 `SandboxedFileSystem` 或 `UnsandboxedFileSystem`，后者使用直接文件操作。
- [受限文件操作](../../codex-rs/exec-server/src/fs_sandbox.rs)：进入受限 helper 的操作仍须获得平台沙箱，否则拒绝。文件写入报错可能是 helper 尚未启动，而非目标文件本身不可写；原始 helper 错误和阶段才可区分。
- [鸿蒙预检](../../codex-rs/linux-sandbox/src/linux_run_main.rs)：`run_bwrap_with_proc_fallback` → `preflight_proc_mount_support` → `build_preflight_bwrap_argv` → `run_bwrap_probe`。挂载命令构造失败会在执行 `run_bwrap_probe` 之前返回。
- [挂载参数](../../codex-rs/linux-sandbox/src/bwrap.rs)和[身份校验](../../codex-rs/linux-sandbox/src/daemon_mounts.rs)：保护 aliases、控制 socket 及其可见别名。本次报告的 `cannot establish app-server socket mount isolation` 来自该检查链。

源码路径指向本分支；以后上游变化需重新核对。本轮不跟进上游更新。

## 如何区分兼容缺陷与能力限制

| 观测结果 | 能支持的判断 | 仍不能证明 |
| --- | --- | --- |
| 当前通用挂载身份错误 | 构造隔离命令前被拒绝 | 不能证明 namespace、proc 或 seccomp 被系统禁止 |
| 同一 Rust FD 的 statx、fdinfo、挂载表明确矛盾 | 可定位具体身份来源和拒绝分支，评估兼容修复 | 不能仅按文件系统名字跳过验证 |
| 身份校验通过，bwrap 实际创建 namespace/mount 被拒绝 | 能力或权限限制成为有依据的方向；需保留原始错误、阶段及身份 | 单一 EPERM 仍不等于所有鸿蒙版本永久不支持 |
| 受限 pwd 成功 | 当前设备和调用路径能够完成该次受限命令 | 不能代替文件编辑、PTY、网络规则与隔离负向验收 |

本轮继续修复挂载识别、保留真实预检失败，以及修正独立探针收尾。没有明确证据就不引入绕过策略。若最终证明当前 HiShell 权限不允许所需能力，再单独评估鸿蒙支持的隔离接口或由用户明确选择不同权限模式。

## 不启用 Codex 沙箱意味着什么

功能上可以执行命令、写文件；这也是上游保留直接路径的原因。它不会自动获得 root，也不会取消鸿蒙自己的目录权限、强制访问控制、签名或进程限制。别名目录和控制 socket 等程序自身的安全校验也不会因此全部消失。

因此，关闭 Codex 沙箱不是当前故障已经修好的证明，人工逐次批准也不是工作目录隔离的等价实现。本轮包不自动切换到全盘访问，不修改用户已有权限配置。
