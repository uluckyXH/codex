# 平台启动与进程首批交付

本批基线为 `c699f82a4b4710248a2c1730d025ea711928a64d`，实施分支为 `codex/harmony-platform`。范围限定为平台启动、Shell 发现与底层进程创建；没有商业鸿蒙 PC，不能以本批结果认定真机可用。

## 已落地的最小修复

### 未切换工作目录时允许使用 POSIX 启动

[POSIX 子进程实现](../../codex-rs/utils/pty/src/posix_child.rs)原有 OHOS 分支通过 `dlsym` 查找 `posix_spawn_file_actions_addchdir_np`。SDK 6.1.1.125 的头文件和 ARM64 `libc.so` 均没有该扩展；此前即使请求没有 `cwd`，也会立即返回兼容后端。这使[辅助进程启动](../../codex-rs/utils/pty/src/spawn_helper.rs)无法继续使用本来不需要目录扩展的 POSIX 路径。

本批保留已有动态查询，仅将扩展的必需条件收窄为“请求指定了工作目录”。没有扩展且有 `cwd` 时仍返回原有兼容后端，不能忽略请求的目录；没有 `cwd` 时允许继续原有 POSIX 创建。辅助进程随后在单线程映像内设置目标目录、环境和终端。空符号保持为 `None`，不会转换成无效函数指针。

[回归测试](../../codex-rs/utils/pty/src/child_tests.rs)直接调用 POSIX 后端，请求不带 `cwd` 的不存在程序，断言得到 `ENOENT`，防止由于目录扩展缺失直接跳过后端。Mac 上运行该测试仅验证公共路径，OHOS 上缺少扩展的分支仍需设备运行。

### OHOS Shell 发现尊重终端配置

[Shell 探测](../../codex-rs/shell-command/src/shell_detect.rs)在 OHOS 上先检查 `SHELL`：必须是绝对路径、已支持的 Unix Shell 类型，且通过 `which` 的可执行文件检查。拒绝相对路径、命令字符串、未知 Shell、目录和不可执行文件；不对环境值做 Shell 求值。无有效设置时继续原有账户 Shell 查询和 PATH 查找。

OHOS 在没有可用用户默认 Shell 时，按 zsh、bash 的顺序查找。这个顺序依据[华为终端环境说明](https://consumer.huawei.com/cn/support/content/zh-cn16089085/)中的默认 zsh 说明；它不证明某个固定 zsh 安装路径存在。最终 sh 回退也先走发现流程；找不到时交给启动器按实际 PATH 查找 `sh` 并报告启动错误，不直接假定 `/bin/sh` 一定存在。

新增宿主可执行的文件系统测试覆盖非标准目录、中文与空格路径，以及无效和不可执行设置。测试使用临时文件，不执行这些文件，不修改宿主的 `SHELL`。

## 已核对但未改写的入口

| 范围 | 证据与本批处理 | 尚需验证 |
| --- | --- | --- |
| [启动加固](../../codex-rs/process-hardening/src/lib.rs) | SDK 声明并导出 `prctl`、`setrlimit`，保留 `PR_SET_DUMPABLE`、核心转储限制、`LD_*` 清理，以及失败时的错误和非零退出 | 普通终端身份实际能否调用；不把符号存在当作权限证明 |
| [arg0](../../codex-rs/arg0/src/lib.rs) | 保留补丁、执行、文件及 Linux 沙箱辅助分派、别名锁和生命周期，不把 OHOS 沙箱路径变为无沙箱 | 真机软链接、签名、再次执行及 Linux 隔离后端能力 |
| [进程父子关系](../../codex-rs/utils/pty/src/process_group.rs) | SDK 有 `prctl` 与 `PR_SET_PDEATHSIG`；失败继续返回原始错误，不改成成功 | 父进程死亡信号、组取消和回收 |
| [自身辅助入口](../../codex-rs/utils/pty/src/spawn_helper.rs) | 保留 `/proc/self/exe` 和早期 `/proc/self/cmdline` 读取；没有证据支持换成猜测路径 | procfs 可读性与签名后二次加载 |
| [描述符处理](../../codex-rs/utils/pty/src/linux_fds.rs) | 本批没有修改 Linux 原有的 `close_range` / procfs 最佳努力处理 | 若两种方式都失败，原实现可能遗留描述符；这仍是隔离验收阻断风险，不能声称已严格隔离 |
| [安装上下文](../../codex-rs/install-context/src/lib.rs)、[构建信息](../../codex-rs/build-info/src/lib.rs)、[后台进程](../../codex-rs/utils/process/src/lib.rs) | 未发现本批需要替换的 Linux 专用实现，保留现有目标信息与 Unix 行为 | 包移动后的资源定位与真实辅助入口 |

本批没有实现或认证新的沙箱后端，也没有关闭现有加固、审批或沙箱。后续若隔离能力检查失败，集成方案必须在执行前给出明确错误；不得将本批的底层进程可编译结果解释为受限命令已安全可用。

## 验证与集成

本批命令、被测源码摘要、退出码、依赖阻塞和未执行项见[独立测试报告](测试报告/2026-10-02-175930-平台启动与进程适配-平台会话/测试报告.md)。输出与临时文件使用本工作副本内独立 `.harmony-build/测试批次` 目录，Cargo 并发固定为 2。

根 `Cargo.toml`、`Cargo.lock` 和第三方依赖补丁留给主会话；本批没有修改它们。Shell 和 arg0 的 OHOS 检查若在已知的 `rustyline/nix` ioctl 问题处失败，需由集成后的目标检查补齐，不能把依赖失败当成源码通过。

登录与认证按用户要求全部未执行，包括真实和模拟测试；没有读取用户凭据，也没有改动登录或提供方配置。公共报告索引和主实施进展由集成会话统一登记。
