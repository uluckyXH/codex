# 交叉编译与原生依赖适配

状态：覆盖适配04—05，完整 ARM64 OHOS release 构建、SDK 自签名、目录包与 Mac 文件安装验证已完成；商业鸿蒙 PC 加载和编码任务仍待真机验收。实际命令见[原生流水线](原生资源构建签名与安装流水线.md)，源码与证据见[实施进展与构建记录](实施进展与构建记录.md)。

## 构建输入

| 输入 | 首轮设计 |
| --- | --- |
| 源码与依赖 | 固定上游提交和对应 Cargo.lock；不为消除错误无依据地更新全部依赖 |
| Rust | 当前仓库固定 1.95.0，随上游同步逐次验证 |
| 目标 | ARM64 候选 `aarch64-unknown-linux-ohos`，设备确定后确认 |
| SDK | 当前构建使用 6.1.1.125 / API 24；最低设备版本、加载器与商业鸿蒙兼容性待验证 |
| 构建机 | 已用 Apple Silicon macOS 完成最小程序及完整 CLI 开发构建和链接 |
| 输出 | 原生 ELF、必要原生库、辅助工具，以及版本和依赖记录 |

Rust 官方提供 OHOS 目标及以 SDK Clang 为链接器的构建方法。它支持形成工具链方案，但不能单独证明 Codex 全部依赖或商业系统兼容。[Rust OHOS 构建说明](https://doc.rust-lang.org/rustc/platform-support/openharmony.html)

## 需要审核的依赖

| 依赖或模块 | 为什么涉及适配 | 拟议处理 |
| --- | --- | --- |
| libc、Tokio、mio、PTY 库 | ABI、事件循环、信号、线程和系统调用 | 审核锁定版本的 OHOS 分支，编译后执行最小接口用例 |
| aws-lc-rs、aws-lc-sys、ring、可能引入的 OpenSSL | C/C++、汇编及目标平台识别 | 以实际 feature 图确认选中项；采用目标工具链，保留所需加密语义 |
| SQLite、sqlx | 捆绑 C 库、离线查询元数据、文件锁 | 确认目标编译和既有离线构建方式；运行行为交给存储专题 |
| tree-sitter 及语法库 | 原生解析器构建 | 核查构建脚本与 C 编译器，验证常用 Shell 解析 |
| keyring、secret-service、zbus、arboard | Linux 桌面服务与窗口系统依赖 | 按目标隔离；运行开关不能代替 Cargo 条件依赖调整 |
| bwrap、libcap | Linux 专用 C 代码和 pkg-config | 由沙箱决策决定是否移植，不能链接宿主 libcap 冒充目标库 |
| V8 与代码模式宿主 | 定制预编译库、绑定文件、可执行内存 | 首轮可暂缓，但必须同步调整完整打包流程 |
| 程序宏和 build.rs | 在宿主运行，却为目标生成代码 | 区分宿主构建与目标构建，防止对所有编译任务套用同一目标工具 |

证据入口：[工作区依赖与补丁](../../codex-rs/Cargo.toml)、[锁文件](../../codex-rs/Cargo.lock)、[状态依赖](../../codex-rs/state/Cargo.toml)、[bwrap 构建](../../codex-rs/bwrap/build.rs)、[V8 说明](../../third_party/v8/README.md)。表内并不表示所有依赖都已确认无法编译。

## 工具链配置草案

推荐使用已落地的[构建脚本](../../scripts/build_harmony.py)，自动生成目标包装器并隔离宿主依赖。下面保留链接器原理示例；完整构建还需 CMake、目标 pkg-config 等输入，复现本仓库时优先使用该脚本。

```sh
#!/bin/sh
exec "/SDK绝对路径/native/llvm/bin/clang" \
  --target=aarch64-linux-ohos \
  --sysroot="/SDK绝对路径/native/sysroot" \
  -D__MUSL__ "$@"
```

这沿用官方工具链示例；还需依据选定 SDK 确认 API 版本参数。C++ 包装器使用同一 SDK 的 `clang++`。`-D__MUSL__` 是 C 预处理条件，不会把 Rust 的 `target_env = "ohos"` 变成 `musl`。

在仓库根目录开始的候选构建步骤：

```sh
cd codex-rs
rustup target add --toolchain 1.95.0 aarch64-unknown-linux-ohos
rustc +1.95.0 --print cfg --target aarch64-unknown-linux-ohos

export CARGO_TARGET_AARCH64_UNKNOWN_LINUX_OHOS_LINKER="/工具绝对路径/鸿蒙链接器.sh"
export CC_aarch64_unknown_linux_ohos="/工具绝对路径/鸿蒙链接器.sh"
export CXX_aarch64_unknown_linux_ohos="/工具绝对路径/鸿蒙链接器加加.sh"
export AR_aarch64_unknown_linux_ohos="/SDK绝对路径/native/llvm/bin/llvm-ar"
export RANLIB_aarch64_unknown_linux_ohos="/SDK绝对路径/native/llvm/bin/llvm-ranlib"

cargo +1.95.0 build --locked --release \
  --target aarch64-unknown-linux-ohos \
  -p codex-cli --bin codex
```

输出候选路径为 `codex-rs/target/aarch64-unknown-linux-ohos/release/codex`；如设置独立目标目录则以实际配置为准。`-p codex-cli` 会编译其传递依赖，不能假定只涉及一个 crate。

`AR` 和 `RANLIB` 都必须选择目标工具。实际完整链接曾因 OpenSSL 构建调用 Mac 的 ranlib，把目标静态库处理成空归档；仅指定 clang 和 llvm-ar 不足以避免混用宿主工具。仓库构建脚本已设置这两个目标专用变量，保留宿主工具不变，失败与修复证据见[归档工具报告](测试报告/2026-10-02-184728-目标归档工具修复-主会话/测试报告.md)。

## 已落地的依赖与编译补丁

| 项目 | 处理与维护边界 |
| --- | --- |
| nix 0.28 ioctl | 本地保留原版本及许可，只为 OHOS 使用 c_int request；不编辑 Cargo 注册表缓存，详见[补丁说明](../../third_party/rust/nix-0.28.0/鸿蒙适配说明.md) |
| Linux 桌面依赖 | OHOS 排除不适用的 arboard / zbus 后端，消除其 nix 0.29 类型错误；终端能力缺口仍明确提示 |
| OpenSSL 归档 | 目标 CC / AR / RANLIB 成套配置，不改变宿主构建工具，也没有关闭 TLS 验证 |
| 编译查询深度 | core 仅在 OHOS 设置 recursion_limit=256，处理发布检查中异步类型布局深度达到 130 的错误；这是编译期上限，不改变运行时栈限制 |

发布检查失败原记录见[集成报告](测试报告/2026-10-02-192224-最终源码集成验证-主会话/测试报告.md)。查询上限调整覆盖 OHOS 的 dev/test/release；其他目标保留原值。上游或 Rust 升级时重新验证是否仍需要，不能用无限提高上限掩盖新的类型问题。

## 构建问题收敛顺序

1. 固定依赖解析，生成实际目标依赖和 feature 图，记录源码、工具链与 SDK。
2. 构建最小 Rust 程序，检查标准库与链接器组合。
3. 处理条件编译和依赖构建错误，再处理符号与动态库错误。
4. 构建 CLI 必需的本地执行路径和辅助程序。
5. 按首版能力清单装配，禁止自动回退下载 Linux ARM64 依赖。

若某 crate 不支持 OHOS，优先隔离可选功能；核心依赖则做最小补丁或经比较后替换。记录补丁版本、上游来源、修改原因和后续移除条件。不能仅靠 `--no-default-features`、跳过 bwrap 构建或打开全局交叉 pkg-config 来宣称问题解决。

pkg-config 若确有必要，使用目标专用的库目录和 sysroot，隔离宿主搜索路径。既有某些 build.rs 会主动找宿主目录，应逐项修正。

## 产物检查与完成标准

使用所选 SDK 的 `llvm-readelf` 检查 ELF 头、程序解释器、动态依赖、RPATH/RUNPATH 与未解析符号。对照目标 SDK 和未来真机记录，不把“ARM64 ELF”当作可执行证明。

构建日志和产物记录应足够让另一台构建机重建同一组合。无设备时可确认“目标编译和静态检查通过”；程序加载、系统调用、加密库实际连接和运行稳定性仍归[验证方案](验证方案与兼容性记录.md)。

本机安装 Rust 并在鸿蒙上自举编译不是首轮前提。运行已编译的 Codex 本身无需完整 Rust 开发工具链；若要编译用户的 Rust 项目，则需另外提供该项目的原生开发环境。
