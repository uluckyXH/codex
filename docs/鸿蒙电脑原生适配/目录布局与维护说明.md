# 目录布局与维护说明

日期：2026-10-04。状态：新布局已写入本轮源码，目录相关 Mac 测试及完整 OHOS 目标检查通过，签名新包与设备验收另行记录；不适用于此前发布的固定 UID 包。开发期间直接采用新布局，不开发旧数据迁移代码；需要时手动转移配置。

实施与进度以[通用身份与目录初始化及终端改造计划](通用身份与目录初始化及终端改造计划.md)为准。本文说明每个目录保存什么、由谁创建、升级时如何保留，以及哪些内容可以清理。

## 一、统一放在一个 codex 目录

在系统提供且验证可用的应用数据目录下，新建专属的 `codex/`。当前应用环境的示例为：

```text
/data/storage/el2/base/files/       系统提供的应用数据目录
└── codex/                        Codex 自身的数据根目录
    ├── state/                    配置、凭据、会话、数据库及其他持久状态
    ├── r/                        受保护的内部运行资源
    │   ├── a/                    命令别名的运行记录、锁及会话资源
    │   └── s/                    app-server 控制 socket 及锁
    ├── tmp/                      本次运行产生的临时文件
    ├── logs/                     Codex、启动器及诊断日志
    ├── workspace/                可选的默认测试项目目录
    └── host/                     仅 GUI 测试宿主需要的辅助数据
        ├── control/              宿主操作请求及状态
        ├── handoff-private/      私有配置导入的短期中转
        └── home/                 测试宿主必要时提供的 Shell HOME
```

`files` 是系统提供的这一层；`codex` 和下级目录由我们的初始化逻辑创建。使用 ApplicationContext 等实际平台来源，不根据 UID 拼接物理路径。不同应用中相同的路径文字可以映射到不同数据空间；读取 UID 只是查询已有进程身份。[官方应用沙箱目录说明](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/file-management/app-sandbox-directory.md)

正式 CLI 从 HiShell 启动时，必须验证其实际目录视图与可用数据根。不能因为测试 GUI 能使用上述路径，就断言 HiShell 也已经验证通过；找不到应用上下文也不等于已经证明该路径不能使用。

这个布局集中管理默认的 Codex 可写数据。签名可执行文件、原生辅助工具仍放在经验证允许执行的安装目录；用户项目可放在有权访问的桌面等位置，不必进入 `workspace/`。已有用户显式配置的 `CODEX_HOME` 和日志位置按兼容规则处理，不强行搬迁。

## 二、各目录的职责与维护规则

| 目录 | 内容与用途 | 创建与保留 | 清理规则 |
| --- | --- | --- | --- |
| `codex/` | 本实例的数据根；记录实际目录来源，供诊断定位 | 首次启动安全创建，以后复用 | 不整体删除，不递归修改系统 `files` 或 HOME 的权限 |
| `state/` | 默认 `CODEX_HOME`；含 `config.toml`、已有凭据文件、会话和数据库，以及上游放在用户目录中的持久资源 | 配置解析前准备；沿用上游文件格式；已有内容不覆盖 | 不按缓存清理；备份应覆盖完整一致状态，禁止只删数据库或凭据来解决启动问题 |
| `r/` | aliases 与控制 socket 的受保护根；它不是普通缓存目录 | 验证所有者、目录来源、防替换与私有性；各子进程使用同一可信选择 | 先检查活跃进程、锁和对象身份；只能清理已确认失效的本实例资源，不能运行中直接删除 |
| `r/a/` | 命令别名的运行记录和锁；平台允许时创建会话别名 | 按别名实现创建；HNP 继续使用已安装的签名别名程序 | 会话正常结束后按所有权回收；不删除安装包中的辅助程序 |
| `r/s/` | app-server 通信 socket 及配套锁 | 启动监听前创建；完整 64 位十六进制名称和冲突检查保留 | 对活跃监听不得删除；过期对象清理仍需验证目录和 socket 身份 |
| `tmp/` | 进程临时文件、处理中间产物 | 按需创建，传给需要该临时目录的 Codex 子进程 | 仅清理已结束任务的临时内容；不扫除整个系统临时目录 |
| `logs/` | 默认 TUI 日志、进程退出信息、目录初始化和工具诊断 | 默认日志入口统一到这里；按来源命名，保留错误及原始退出状态 | 支持轮转和有限保留；故障处理中保留对应证据；不记录 Key、令牌或完整认证配置 |
| `workspace/` | GUI 默认测试项目；用户可在这里创建文件 | GUI 使用默认项目时按需创建；CLI 默认保留调用者 cwd 或显式 `--cd` | 属于项目数据，不自动清理、不随升级删除 |
| `host/` | GUI 测试入口的控制和导入功能，正式 CLI 不依赖它 | 只有测试宿主启用相应功能时创建 | 控制记录可按会话回收；私有导入完成后回收中转内容，不输出密钥 |
| `host/home/` | 普通应用环境没有合适 Shell HOME 时使用的测试宿主专用目录 | 仅宿主需要时提供 | 可能含用户的 Shell 配置，应保留；从 HiShell 启动时不替换用户原有 HOME |

新建自身私有目录使用经平台验证的保护模式，敏感文件限制访问。普通项目目录不要求归属应用 UID 或模式为 0700。系统提供的父目录要验证，但不对共享父目录执行全局 `chmod`；仅有一个 0700 子目录不能自动证明其可被替换的父目录可信。

## 三、socket 长度必须随目录改造一起处理

当前源码 `codex-rs/uds/src/ohos_runtime.rs` 在运行根下面再创建 `c<UID十六进制>/s`，并为完整 64 字节 socket 名称及结尾 NUL 预留长度。本机 OHOS SDK 的 `sys/un.h` 声明 `sun_path[108]`。

| 路径布局 | 包含 64 字节名称及结尾 NUL 的字节数 | 结论 |
| --- | --- | --- |
| 当前 `files/r/c00000000/s/<名称>` | 108 | 当前示例刚好到达上限 |
| 直接加一层 `files/codex/r/c00000000/s/<名称>` | 114 | 超限，不能只替换路径前缀 |
| 拟议 `files/codex/r/s/<名称>` | 104 | 当前示例长度可容纳，仍需目标运行验证 |

以上按表中的完整 `/data/storage/el2/base/` 前缀计算。拟议方案利用已经按实际进程身份验证的应用私有根区分身份，去掉内部多余的 UID 路径层；所有者检查、父目录保护、锁、完整摘要、对象重验证和对端身份检查必须保留。不同应用目录视图必须分别验证。

实际数据根较长时仍按字节计算，包含中文路径的 UTF-8 长度。不能截断 socket 摘要、跳过长度判断或退回公共临时目录；若需要其他短路径机制，须单独验证后再纳入支持范围。

## 四、初始化和配置定位

1. 获取实际 UID/GID 和平台数据目录来源，不依赖 `id` 命令，不固定某台模拟器的编号。
2. 打开并验证父目录，安全创建或复用 `codex/` 及必要子目录。目录不存在、目录存在但无权访问、所有者不符分别报告。
3. 在配置解析、PATH aliases 和 app-server socket 初始化之前完成目录准备；CLI 自身负责，GUI 调用同一套逻辑。
4. 无用户覆盖时，配置使用 `codex/state/`、日志使用 `codex/logs/`、临时文件使用 `codex/tmp/`。CLI、TUI、`exec`、工具和安装入口保持一致；不能让普通工具环境变量任意改选受保护通信根。
5. 程序在调用者的 cwd 或 `--cd` 指定的项目中工作；创建内部目录不应改变项目位置。GUI 的默认 `workspace/` 只是启动选项。

已有显式 `CODEX_HOME` 优先按上游语义及对应保护要求使用，不覆盖其中的文件，也不把它当作控制 socket 根。这是原有配置能力，不增加旧布局自动转换。保留账号登录和 API Key 配置格式及功能；本轮不发起登录测试，模型保持 `gpt-5.6-terra`。

## 五、开发期间直接使用新布局

本轮不实现旧数据迁移，也不实现旧布局自动发现、迁移恢复、冲突合并或版本回退。新代码按上述目录初始化；旧会话、数据库、日志、Shell HOME 和测试项目不要求搬入新版，旧数据转换也不列入本轮测试。

必要配置按以下方式准备：

1. 新版初始化完成后，由执行者手动把需要的 `config.toml` 放到实际数据根的 `codex/state/config.toml`，不为这个一次性操作编写迁移代码或脚本。
2. 保留现有请求地址、Key 和 `gpt-5.6-terra` 模型配置；配置保持私有，不能进入 Git、安装包或日志。
3. 新日志直接写入 `codex/logs/`，旧日志不自动归集。新项目可在 `codex/workspace/` 或用户选择且有权访问的位置创建。
4. 初始化、当前配置读取、日志导出和打包说明统一改用最新目录；交付时给出新路径和必要的手动配置步骤。

用户显式指定 `CODEX_HOME` 或项目位置时继续支持该配置，不自动搬动其内容。取消迁移开发不等于要求删除旧目录或用户文件；配置准备和设备数据操作在相应测试批次另行记录。

## 六、项目权限和维护入口

在同一 HiShell 中，普通命令能读写某个项目时，应以相同进程身份和目录视图验证 Codex 的对应操作；还需记录是否存在 Codex 自身受限模式、托管网络等额外策略。用户在文件管理器中能编辑，不等于 HiShell 已获得同等授权。

鸿蒙的桌面、文档、下载访问权限可以在“设置 → 隐私和安全 → 文件和文件夹”中管理；具体授予哪个承载应用，以及 Codex 子进程能否使用，应以实际入口验证。[华为官方权限说明](https://consumer.huawei.com/cn/support/content/zh-cn16046673/)

维护时先查看目录来源、当前身份、最终数据根、`CODEX_HOME`、日志位置、项目 cwd、权限模式、源码 SHA 和失败阶段。诊断输出目录摘要，不输出配置文件内容。启动日志尚不能建立时，要在终端标准错误中显示初始化失败原因。

新包发布时，在更新说明中列出本包实际目录、英文命名的安装脚本、必要配置的手动放置位置和日志查看命令。我们负责构建与模拟器调试，商业鸿蒙 PC/HiShell 由用户验收。旧包排障仍使用对应版本的安装与日志文档。
