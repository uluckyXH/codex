# 运行安全与系统路径核对

本轮实现位于独立工作副本 `平台适配` 的 `codex/harmony-runtime` 分支。主会话负责完整 CLI 发布构建、原生辅助工具、签名和整合。本轮未执行主 CLI、登录、认证、凭据存取或模型请求；没有鸿蒙电脑运行结果。

## 探针必须取得真实退出结果

新增 `codex-sandboxing::probe` 统一观察 Unix 探针：启动错误、读取错误、等待错误、超时和超量输出均保持错误；每个输出流最多保留 64 KiB。探针拥有独立进程组，观察失败时结束子进程并回收。探针主进程结束后不再等待后代关闭管道，防止继承 stderr 的进程无限拖延检测。

系统 bwrap 的命名空间诊断和 `--help` 能力检测采用同一限时观察器；仅成功退出构成成功证据。已知命名空间错误保留专门诊断，未知非零退出保留状态和 stderr，命令或加载器启动失败保留具体错误。OHOS 的系统 bwrap 能力失败还会输出错误来源，避免只剩一个无上下文的“不可用”。

实际沙箱预检仍使用选定的 bwrap 启动器；已验证描述符执行的 `bundled_bwrap.rs` 没有修改。OHOS 按请求的 proc/PID 模式预检，包括显式不挂 proc 的请求。未知失败、超时和挂 proc 失败均阻止实际命令，不自动改成无沙箱或减弱隔离。普通 Linux 的既有 proc 兼容重试保留。

`exec-server/src/process_sandbox.rs` 和 `fs_sandbox.rs` 已在需要沙箱但选成 None 时返回请求错误，`sandbox_selection.rs` 使用 Require。检查范围内未发现失败后自动改用 None 的重试。显式请求无沙箱的原有语义未改动。

## 原生探针命令与最小读取路径

两条 bwrap 探针复用同一 `true` 命令解析。OHOS 先查 `/system/bin/true`，再查 `/usr/bin/true`、`/bin/true`，最后查 PATH；只有实际可执行文件才会选中。缺失或不可执行时返回明确的命令缺失错误，不把它归类为命名空间不支持，也不当作探测成功。非 UTF-8 路径在构造当前 String 参数接口时明确失败。

只发现原生命令还不够：`:minimal` 原来没有 OHOS 工具和动态库根。本轮在 `target_env = "ohos"` 下加入 `/system/bin`、`/system/lib`、`/system/lib64`、`/system/etc`、`/vendor/lib`、`/vendor/lib64`，只在路径存在时通过既有只读绑定逻辑加入。显式 deny 仍随后覆盖，用户目录和 `/data` 没有成为隐式读取根，写入范围也未改变。普通 Linux 的默认根清单不增加这些目录。

2026-10-02 查阅的公开依据：

- [OpenHarmony hdc 文档](https://raw.githubusercontent.com/openharmony/docs/master/en/application-dev/dfx/hdc.md) 的交互命令说明用 `/system/bin` 枚举设备工具，并明确命令会随系统版本变化。
- [OpenHarmony toybox 构建定义](https://raw.githubusercontent.com/openharmony/third_party_toybox/master/BUILD.gn) 的标准系统目标包含 true.c、true 别名和 system 镜像安装配置。这支持将 `/system/bin/true` 作为需实查的候选，不证明所有商业 PC 镜像都有此工具。
- [OpenHarmony C/C++ 标准库机制](https://raw.githubusercontent.com/openharmony/docs/master/zh-cn/application-dev/napi/c-cpp-overview.md) 说明系统、NDK 动态库命名空间的系统和 vendor 库搜索路径。只读挂载不会绕过系统自身的库命名空间约束。
- [musl aarch64 命名空间配置](https://raw.githubusercontent.com/openharmony/third_party_musl/master/config/ld-musl-namespace-aarch64.ini) 给出 `/system/bin`、`/system/lib64`、`/vendor/lib64`、`/system/lib` 等实际配置。[动态加载器源码](https://raw.githubusercontent.com/openharmony/third_party_musl/master/ldso/linux/dynlink.c) 使用 `/system/etc/MUSL/generic/version.txt`；[构建定义](https://raw.githubusercontent.com/openharmony/third_party_musl/master/BUILD.gn) 将命名空间配置安装到 system 的 etc。

这些依据来自公开 OpenHarmony 布局，并非商业鸿蒙电脑测试。特定镜像还有额外库目录时，应按实际依赖和权限补充；本轮未把整个 `/system`、`/vendor`、`/data` 或根目录作为宽泛兜底。缺库、权限、签名或加载失败必须保留诊断并停止受限命令。

## 主入口加固顺序

CLI 通过 `arg0_dispatch_or_else` 进入 `arg0_dispatch`。本轮把 OHOS 主进程的 `pre_main_hardening` 接在 helper 分发之后、dotenv 加载之后、别名准备及线程/运行时创建之前。复用 linux-sandbox 已有的 process-hardening 依赖，不改工作区 Cargo.toml 或 Cargo.lock。

PTY、沙箱、exec、文件系统等 re-exec helper 在前面分发并结束其流程，保留显式传入的子进程环境；普通主入口则清理 dotenv 可能恢复的 LD_*，并执行既有的不可转储和 core 上限设置。初始化失败退出，不继续普通启动。该清理限制后续进程加载环境，不意味着可以撤销当前进程在进入 Rust 前已发生的动态加载。

独立宿主探针直接编译现有 process-hardening 源码，验证标记变量清理和 core 软硬上限，不读取 Codex 配置。OHOS 对应探针只编译/链接，设备侧 PR_GET_DUMPABLE 和权限效果待验证。

## 文件监控、目录与会话存储的只读核对

| 范围 | 源码证据与处理 |
| --- | --- |
| 文件监控 | file-watcher 使用 notify::recommended_watcher；当前 notify 的 Linux cfg 覆盖 OHOS 的 Linux target_os。初始化错误由库返回；app-server 的 fs_watch 与 skills_watcher 会记录警告并使用 noop。未取得设备失败证据，本轮未改成轮询，也未宣称实时通知可用。 |
| 主目录 | utils/home-dir 优先使用经过目录与 canonicalize 校验的 CODEX_HOME，否则调用 dirs::home_dir；没有把用户目录硬编码成 /home。 |
| 绝对路径 | utils/absolute-path 对顶层符号链接别名做一般化处理；核对的 /tmp 引用多为测试夹具，没有据此改写用户路径。 |
| 会话写入锁 | rollout/writer_lock 从配置的 codex_home 派生目录；try_lock/lock 的失败保持错误，锁竞争保留 WouldBlock，没有伪装取得锁。 |
| SQLite | state 的 SqliteConfig/state_db_path 从配置目录构造数据库路径。没有依据要求另建鸿蒙专用存储根；WAL、锁、原子替换和权限效果仍须设备测试。 |

本轮只修复已有代码中可定位的探针、入口顺序与原生系统路径缺口；以上读取没有接触真实用户配置、会话数据库或认证缓存。

## 设备验证边界

交叉检查、目标测试二进制链接和 ELF 检查不能替代设备执行。后续应在同一签名候选版本上核对：原生 true 与依赖库可见；bwrap 已验证描述符启动可用；用户/挂载/PID/网络命名空间和 seccomp 的实际返回；受限策略的读写和 deny 效果；主进程加固后 helper 重入；inotify 通知；会话锁与 SQLite 持久化。任何不支持或未知结果应保留错误，不能以默认放开权限补偿。

各批命令、源码身份、失败原因、通过数量和产物 SHA256 见测试报告目录。本轮代码未改变签名执行方式、TUI、功能开关、原生 bwrap 打包构建或根依赖锁。
