# 上游同步与版本维护

状态：覆盖适配28，维护分支已建立并开始首批补丁；尚未进行后续上游版本的同步演练。源码同步从适配阶段开始设计，用户端应用更新机制另行处理。

## 维护原则

继续使用 Codex CLI 上游核心，平台差异集中在既有模块边界。避免复制整个核心或维护一套独立配置、会话格式和工具协议。对第三方依赖的补丁与 Codex 自身改动分别记录。

当前[贡献规则](../../docs/contributing.md)说明不接受外部代码 PR，因此不能把“先让 OpenAI 合入全部鸿蒙补丁”设为计划前提。设计上仍保持补丁清晰，便于持续同步和将来替换实现。

## 分支与版本约定

已建立 `codex/harmony-native`，`origin` 已核实为个人 fork `uluckyXH/codex`。下面其余同步流程为后续维护约定；当前尚未新增 `upstream` 远程或执行版本合并。

| 用途 | 建议 |
| --- | --- |
| 官方上游 | 用 `upstream` 指向经核实的官方仓库；操作前检查现有配置 |
| 鸿蒙维护分支 | `codex/harmony-native`，保存可追溯的适配提交 |
| 单次同步分支 | `codex/harmony-sync-<上游版本>`，从维护分支创建 |
| 上游基线 | 明确 release/tag 加实际提交 SHA，不记录含糊的 latest |
| 适配版本 | 与上游版本分别记录，能定位具体补丁集合和功能裁剪 |

正式维护分支采用保留上游历史的合并方式。个别安全修复若提前选择提交，需要记录来源，下一次整体合并时核对是否重复。已共享维护历史不随意改写。

## 补丁怎么分层

1. 目标识别、SDK 和构建输入。
2. 系统接口、进程、文件和权限后端。
3. 凭据、终端及可选能力隔离。
4. 资源、打包、签名和安装识别。
5. 与真实行为变化对应的测试、诊断及说明。

每个补丁解决一个可描述的问题，说明上游假设、鸿蒙差异、验证证据和撤销条件。平台调整不顺带做无关重构或批量格式化，降低后续冲突范围。

## 一次上游同步的流程

| 步骤 | 操作 | 留下的证据 |
| --- | --- | --- |
| 选择版本 | 阅读官方发布变化，确定目标 tag/SHA | 选择理由及版本身份 |
| 差异评估 | 对照源码清单检查工具链、依赖、协议、配置及新增入口 | 受影响任务编号与潜在冲突 |
| 独立合并 | 在同步分支合并并逐项解决冲突 | 可复核的合并和修复提交 |
| 构建收敛 | 使用该上游要求的 Rust、锁文件和经验证 SDK | 构建日志及依赖变更 |
| 重新装配 | 处理新增辅助程序、默认特性和资源 | 完整包与能力清单 |
| 重新签名 | 对最终变化产物签名并计算摘要 | 签名记录与最终文件摘要 |
| 验证 | 运行受影响回归与原生编码任务 | 与基线对比的结果 |
| 数据兼容 | 用旧版数据副本验证新版本读取和迁移 | 兼容范围、不可逆变化及限制 |
| 接收 | 达到约定证据级别后合并回维护分支 | 适配版本与兼容性记录 |

没有真机时可以完成候选同步，但状态必须保留“未真机验证”，不能把过去版本的运行结果复制成新版本的通过记录。

## 每次必须复核的范围

- `rust-toolchain.toml`、Cargo.lock、工作区补丁、SDK 和链接参数。
- Linux/Unix 条件、进程加固、PTY、辅助进程及沙箱选择。
- 新增系统调用、环境变量、动态库及第三方运行时。
- 配置字段、功能默认值、模型要求、工具注册和宿主预热。
- 包布局、安装来源识别、手动和后台升级入口。
- 登录、MCP OAuth、网络代理和自定义证书。
- 数据库迁移、会话格式及目录布局。

## 当前不设计的内容

自动更新频率、用户下载渠道、差分包、热替换、版本回退界面和应用市场上架均待原生 CLI 稳定后设计。当前仅阻止不匹配的上游更新路径，并确保构建版本、签名和数据兼容证据可追溯。
