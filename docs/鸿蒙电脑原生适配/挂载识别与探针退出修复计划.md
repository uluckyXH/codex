## 挂载身份决策

目前已知 C 探针 `dev=66699`，挂载表 `0:66699`；当前 Rust/libc 和 SDK 宏都把该原值解码为 `260:139`。这足以构造失败用例，尚不能证明失败 Rust 进程一定读取相同数值或走了相同分支。

优先调查同一已打开目录的 `statx` 明确设备号与 mount ID。若接口和身份交叉校验可建立可靠关联，可在 OHOS 使用该来源，记录与传统 `st_dev` 解码的差异；其他平台保持已有策略。无支持、字段缺失或交叉校验不一致时必须显式拒绝或回到原有严格路径，不能将错误改写为成功。实际采用方案、未采用原因及测试证据写入本计划的执行记录。

日志要区分 aliases 和控制 socket，并说明读取来源、实际 PID、mount ID、具体拒绝原因。完整挂载表只在显式诊断时输出，采用边界和转义，不读取配置正文、认证或进程环境。

## 验证要求

用户追加能力边界问题已核查，见[鸿蒙沙箱能力与执行方式分析](鸿蒙沙箱能力与执行方式分析.md)。当前故障发生在 bwrap 预检命令构造阶段，不能提前判定系统不支持。命令和文件操作存在非沙箱路径，但本轮不自动切换；需要先分别验证身份检查、实际隔离创建和工具闭环。

- 挂载：设备号不一致、statx 字段缺失/调用失败、inode/mount ID 冲突、重复 ID、隐藏挂载、别名和嵌套挂载；正常可遮蔽别名仍正确处理。
- 探针：无上下文、库/符号缺失、调用中信号和超时、危险析构、输出失败或截断、实际 EUID 路径、原有目录安全检查。
- 交付：诊断脚本失败留档及现有安装边界；真实目标 ELF、四个资源签名信息、包摘要、解包清单、中文路径安装和已有安装拒绝覆盖。
- 不能在 Mac 执行 OHOS ELF。交叉测试 `--no-run` 只算编译链接通过。不要以 0 项测试或合成接口夹具宣称真机支持。
