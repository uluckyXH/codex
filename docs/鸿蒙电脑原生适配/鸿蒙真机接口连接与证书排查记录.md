## 三、配置核对结论

用户当前配置使用 `model_provider = "proxy"` 与 `[model_providers.proxy]`，填写自己的 `base_url`，并设置 `requires_openai_auth = false`、`wire_api = "responses"`、`experimental_bearer_token`。

这一接入形式受当前源码支持，不要求改名为 `harmony_api`，也不要求改用 `env_key`。固定 token 由[提供方认证实现](../../codex-rs/model-provider/src/auth.rs)读取；显式地址由[提供方定义](../../codex-rs/model-provider-info/src/lib.rs)采用。若服务入口是 `/v1/responses`，基址填写到 `/v1`。日志中的 `api_path="/responses"` 是接口路径信息，不能据此断言实际请求漏掉了 `/v1`。

`name = "OpenAI"` 可以保留，不会覆盖显式 `base_url`；源码也用此名称判断部分提供方行为，因此并非完全只有显示用途。模型名称、推理强度和工具能力是否被服务支持，仍需服务响应证明。当前没有足够证据把连接失败归因于配置格式或 Key 错误。

## 四、源码发现的证书加载疑点

1. [HTTP 依赖清单](../../codex-rs/http-client/Cargo.toml)针对 OHOS 启用了 `native-tls` 的 `vendored`，用目标 SDK 编译 OpenSSL。它解决的是目标加密库的构建与链接，不会自动把鸿蒙系统的可信 CA 证书库一起装入程序。
2. [锁文件](../../codex-rs/Cargo.lock)中的 `native-tls 0.2.14` 使用 `openssl-probe 0.1.6`。本机锁定依赖源码的 `candidate_cert_dirs()` 与 `probe()` 文件搜索组合没有覆盖 `/etc/ssl/certs/cacert.pem` 这个完整文件路径。它仍可能通过环境变量、其他候选文件或证书目录加载信任根，实际结果必须看设备日志。
3. 因而存在一个具体假设：curl 找到了上述 CA 文件，而 Codex 的默认 TLS 路径没有加载到所需根证书。这是客户端适配疑点，**不是已确认的根因**，也不能据此宣称网站证书有错或交叉编译生成了错误证书。
4. [自定义 CA 实现](../../codex-rs/http-client/src/custom_ca.rs)优先读取 `CODEX_CA_CERTIFICATE`，其次读取 `SSL_CERT_FILE`。设置非空 CA 文件后，HTTP 客户端还会调用 `use_rustls_tls()` 并加入该文件的证书。因此设置变量后成功，只能进一步指向 TLS 实现或证书加载差异，不能单凭这一结果把问题唯一归因于文件路径。
5. [传输错误映射](../../codex-rs/http-client/src/transport.rs)和[错误日志摘要](../../codex-rs/response-debug-context/src/lib.rs)没有在截图对应的错误文字中展开完整错误来源链。仅有 `error sending request` 不能确认具体的证书校验错误。

HTTPS 的 CA 证书库用于验证远端服务身份，与[鸿蒙可执行文件签名](构建打包与签名设计.md)用途不同。本次排查不需要制作新的自签名 CA，也不以关闭证书校验作为修复方案。
