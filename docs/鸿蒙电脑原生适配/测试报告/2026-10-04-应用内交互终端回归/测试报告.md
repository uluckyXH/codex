# 应用内交互终端回归

测试范围：普通应用 `com.codex.emulatorhnp`、应用UID/GID20020059、官方私有HNP、已签名本地测试程序。测试不调用模型、不读取真实配置内容，不从Ark运行时fork，不修改系统权限。完整Codex界面和真实模型请求由主会话单独验收。

## 基础PTY能力已通过

独立原生 `pty_probe.c` 先openpty，显式检查窗口及termios，再以 `posix_spawn + POSIX_SPAWN_SETSID` 重启自身为子程序。file_actions在新会话打开slave接入stdin/stdout/stderr。

| 项目 | 实测结果 |
| --- | --- |
| openpty | 成功，slave为`/dev/pts/0`。 |
| 初始窗口 | 设置与回读36×120成功。 |
| 原始输入模式 | tcgetattr/tcsetattr成功，恢复后termios各字段一致。 |
| 进程及控制终端 | 子程序SID/PGID均自身PID，标准FD 0/1/2均为TTY，`/dev/tty`可打开。 |
| 输入与输出 | 父子K/R交互通过。 |
| 动态窗口 | master设置44×132后，子程序从控制终端回读相同尺寸。 |
| 退出回收 | 子程序exit23、raw wait5888、signal0；父程序exit0，`PTY_PROBE_PASS`。 |

注意：该基础探针在动态resize后由子程序读取尺寸，未证明父进程可以从master读取尺寸；下面的会话模块另行验证。

## 会话模块设计

实际宿主中的 `pty_session.cpp/.h` 提供固定Codex交互入口，记录源码摘要但不在报告中重复复制生产实现。

- 仅固定应用目录与编译时HNP包路径；模型固定gpt-5.6-terra，初始策略read-only、on-request。
- 页面加载不启动Codex，只有用户点击开始才启动；准备目录和导入配置由宿主既有入口处理。
- 单次输入最多16KiB，整次进入64KiB有界队列才返回成功；队列满拒绝且不写入该次内容，后台保留系统partial-write的剩余部分。
- 非阻塞读取每次最多16KiB，真实Codex终端内容仅通过base64返回界面，不写入日志；本报告只记录固定dummy程序的公开测试标记。
- 窗口行列各1..1000且面积不超过100000，非法请求不执行ioctl。
- 独立watcher负责waitpid，停止时针对仍未回收的本次子进程TERM，1秒后仍不退出则KILL；UI销毁主动调用Stop。

## 会话层目标回归

第三版探针测试使用与当时生产会话模块逐字节相同的C++源码（SHA256 为 `7a41f1bce86912bcf2e44a9638ba463f93b85fb0e8256c93a6cbac3c753e5505`），仅把测试头文件的固定包路径指向dummy程序；不启动Codex或访问模型。dummy验证固定参数、TTY身份、16KiB完整输入、窗口、正常exit37，以及忽略TERM后的KILL回收。

第一次结果：Start成功，键盘K传递成功；步骤7（非法尺寸拒绝和合法动态尺寸回读）失败，探针退出7/raw1792。保留原始失败，没有把底层PTY通过描述为会话模块全部通过。

第二版已定位：非法尺寸按预期拒绝；合法resize的master `TIOCSWINSZ`成功，但master `TIOCGWINSZ`返回EACCES 13（`resize_get`）。因此基础探针与会话层结果并不冲突，基础探针由slave读取实际尺寸。

最小修复：保留本次openpty创建的原始slave文件描述符作为尺寸观察端（CLOEXEC），设置尺寸仍走master，回读走slave；不重新打开可被替换的命名路径。watcher在waitpid回收子进程后立即关闭slave观察端，再排空master输出，避免额外slave引用导致EOF不出现。没有跳过尺寸回读，也没有修改内核或SELinux策略。

第三版目标回归全部通过，父探针exit0/raw0，最终 `PTY_SESSION_PROBE_PASS`：

| 会话验收项 | 结果 |
| --- | --- |
| 启动 | 固定Codex参数由dummy核验；首次Start成功，运行中再次Start拒绝。 |
| 输入界限 | 16385字节请求拒绝；16384字节请求完整送达、逐字节核验，partial-write余量没有丢失。 |
| 窗口 | 非法1001列拒绝；132×44合法尺寸设置及slave回读成功，子程序再次核验。 |
| 正常结束 | dummy输出完成标记，exit37被准确回收。 |
| 重启会话 | 同一模块可启动第二个独立PTY子进程。 |
| 队列背压 | 64KiB输入队列满时整次拒绝，返回input_queue_full、accepted0。 |
| 停止与回收 | 第二个dummy明确忽略TERM，watcher按时发送KILL并准确回收signal9。 |
| EOF | 子进程回收后slave观察端关闭，最终master读取eof=true，未因额外FD保留卡住。 |

这证明本测试应用中的终端会话层可用。完整Codex的界面渲染、真实模型请求及工具行为仍需主会话对应的完整包记录，不将dummy验收算作模型或沙箱能力验收。

## 复现与证据

生产实现只保留在[终端会话源码](../../../../harmony/terminal-host/entry/src/main/cpp/pty_session.cpp)，本报告不复制该实现。最小probe构建时将该文件放入临时隔离目录，固定测试头文件把 `CODEX_HNP_PACKAGE_PATH` 设置为 `/data/app/codexnetprobe.org/codexnetprobe_0.1`，与 `session_probe.cpp` 一起交叉编译；dummy由 `pty_test_child.c` 构建。两份程序经SDK自签、正常HNP安装，dummy命名同包 `bin/codex`，应用启动 `bin/pty-session-probe`。

`evidence_metadata.json`保留第三版回归时生产实现与测试实现逐字节相同的校验，以及探针、签名程序和原始输出SHA256。测试只替换独立探针包中的dummy，最终 `codexharmony` 安装包不受该测试替换影响。

最终宿主集成时，仅在固定 Codex 参数中增加 `-c 'log_dir="/data/storage/el2/base/files/state/log"'`，使上游 TUI 创建可定位的诊断日志。已逐行核对，和第三版探针源码的唯一差异是该固定日志参数；PTY、输入输出、窗口、回收逻辑及模型、沙箱策略均未改动。最终 C++ 源码 SHA256 为 `5edf0e10d295964b4b03b5311017727215df157f62e9776ae67da34f79f0151e`。因此不声称最终文件与此前探针源码仍逐字节相同；最终真实 TUI 与日志生成另由主会话验收。
