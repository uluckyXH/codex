# HNP 应用目录与内部命令入口回归

## 结论与适用范围

本次适配使用普通应用 `com.codex.emulatorhnp` 通过官方私有 HNP 安装原生程序，部署策略显式命名 `hnp-debug`。当前已安装应用的 UID/GID 为 `20020059`，构建时绑定此 UID；卸载重装导致 UID 改变时应重新核实并构建。它不是面向所有商业 PC 的通用安装契约，也不把 HDC UID 2000 当作应用身份。

本报告覆盖运行目录和内部工具入口。完整 Codex 模型请求、TUI、命令沙箱和用户操作界面由主会话后续完整包验收，不能用本报告代替。

## 已确认的系统行为

| 项目 | 观测与处理 |
| --- | --- |
| 正常应用联网 | 同一自签原生 ELF 通过普通 `INTERNET` 应用的官方 HNP 安装后，公开端点 4/4 IPv4 TCP 连接通过；HDC 直接运行的 EACCES 不代表这个应用上下文不可联网。 |
| Context 全局 filesDir | `/data/storage/el2/base/files`；应用级目录不是较长的 `haps/entry/files`。 |
| 运行目录祖先 | `/`、`/data`、`/data/storage`、`/data/storage/el2` 均 root:root/0711。 |
| 应用数据父目录 | `base`、`files` 最初为应用自身 UID/GID、0777；专用宿主用不跟随链接的文件描述符核验归属后收紧为0700，停止/重启应用后保持。没有修改用户 HOME，没有在 Rust 校验中接受0777。 |
| 运行根 | `/data/storage/el2/base/files/r`，30字节，应用自身0700，保留完整64位十六进制控制 socket 文件名。 |
| 私有 HNP 安装树 | `/data/app`、`.org`、版本目录、`bin`、`codex-path` 均3060:3060/0775，普通 ELF 为3060:3060/0755。 |
| 系统挂载与标签 | `/data/app` 来自 `/app/el1/bundle/100/hnp/com.codex.emulatorhnp`，ext4、rw/nosuid/nodev；安装树标签 `private_hnp_file`。这里只记录证据，没有用标签字符串代替路径安全校验。 |
| 应用组成员 | 父应用与 HNP 子进程的 UID/EUID/GID/EGID 均20020059，附加组1097、3099，不含安装器组3060。 |
| 符号链接 | HNP应用在私有0700目录创建 symlink 返回 EACCES 13。不能继续依赖动态创建四个 Codex 工具别名。 |

原始系统观察由另一协作会话采集：`.harmony-build/emulator-hnp/hnp-host-tightening.log`、`hnp-host-restart.log`、`hnp-directory-child-restart.log`、`extras-hnp-directory-child.txt`、`groups-parent.log`、`groups-child.log`。这些日志不包含接口密钥。

官方应用目录设计依据：[应用沙箱目录](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/file-management/app-sandbox-directory.md)。Context 路径、挂载位置和本次镜像权限分别以实际探针结果为准，不把上游说明等同于所有 HarmonyOS 版本的能力承诺。

## 实现与安全边界

- `CODEX_OHOS_RUNTIME_PROFILE=hnp-debug`、固定30字节根和 `CODEX_OHOS_RUNTIME_UID=20020059` 在编译时确定；运行时环境不能换根、换UID或切换部署策略。`strict` 与 `hdc-debug` 路径保持各自原有规则。
- 运行数据目录继续完整逐级检查归属、权限、类型、无符号链接和文件描述符身份，保留 FD、重验、CLOEXEC 与私有0700要求。
- `scripts/harmony_hnp_alias.c` 是小型原生入口，SDK 自签后原样复制为 `apply_patch`、`applypatch`、`codex-linux-sandbox`、`codex-execve-wrapper` 四个普通 ELF。不会复制四份大型 Codex，也不创建系统不允许的链接。
- Rust 在初始化时检查它们属于当前运行的同包 `bin/codex`，逐级不跟随链接并持有所有路径 FD，核验主程序 inode/dev 与 `/proc/self/exe` 一致；每个入口的 SHA256 必须等于构建时 `CODEX_HNP_ALIAS_SHA256`。摘要不能由运行时环境覆盖。
- 入口程序依据自己的真实安装文件名选择原始 `argv[0]`，保留其余参数，然后执行同包 `bin/codex`，复用原有 Rust arg0 分派。
- 官方安装器目录0775必须单独建模：仅 `/data/app` 安装子树的**精确3060:3060/0775目录**允许安装器组写入；信任的是操作系统安装器用户及组。应用 EUID 必须是应用范围，EGID及所有附加组不得包含3060。普通 ELF 仍不得由组/其他用户写入，不得有特殊权限位；该例外不适用于运行数据目录或任意0775目录。
- 安装器可信并不意味着应用可以改写包。入口缺失、同包身份错误、权限/归属变化、路径或文件替换、SHA256不符均拒绝启动，不回退到未校验入口。

## 测试过程与结果

1. 第一版目标运行目录测试：目录、锁创建与锁验证均通过，随后测试为制造负样本调用 symlink 时被平台拒绝；原始测试以101退出。控制 socket 独立生命周期测试通过。保留原失败证据，不将它描述为全项通过。
2. 将平台能力探测与目录验收拆开：目录/锁测试不再要求操作系统支持 symlink；新增目标能力测试明确预期创建链接返回 PermissionDenied。原有 Mac 链接拒绝安全负测保留。
3. 第一版入口程序对0775安装器目录严格拒绝，四入口均以126退出。根据实际UID/GID/权限与组成员证据加入上述精确安装器契约，再复测。
4. Mac `codex-uds --lib`：33/33通过。HNP UID绑定、未知/缺失/错误UID、固定根限制、0777共享目录与外国所有者拒绝均有覆盖。
5. Mac 最小别名测试 harness 直接包含生产两个模块：16/16通过（原动态入口4项、新安装入口12项）。覆盖内容摘要篡改、同摘要inode替换、目录替换但叶子硬链接身份保留、每级FD/CLOEXEC、错误布局、当前主程序身份错配、链接、特殊权限位、错误所有者、超大入口、安装器GID错配、补充组含3060和任意0775路径拒绝。
6. 目标 HNP 原生生产模块验证：`profile=hnp-debug`、UID20020059下，四入口均转发正确的 `argv[0]` 与参数、子程序退出0，最终 `HNP_ALIAS_VALIDATION_PASS`；父应用真实 wait 状态exit0/raw0。
7. 拆分后的目标运行目录/锁、64hex socket生命周期、symlink能力三项测试：3/3通过。这里只把平台禁止创建链接记录为能力事实，没有宣称支持符号链接。
8. `git diff --check`通过；交叉编译验证器与测试程序成功，SDK签名静态检查成功。完整CLI生产集成编译和UI验收仍由主会话完成。

测试没有切换完全权限、关闭 SELinux、授予系统身份、修改用户整个 HOME 或探测实际接口密钥。本次构建与签名只证明 ELF 生成及指定模拟器部署结果；完整 Codex 集成另行验收。

## 可复现入口

Mac 测试使用外置盘 Cargo/Rustup 缓存。别名最小 harness 放在 `.harmony-build/runtime-profile-tests/alias-harness`；本目录保存对应 `Cargo.toml`、`alias_test_lib.rs` 和 `alias_probe_main.rs`。源文件通过 path 属性直接引用生产实现，不复制一份校验逻辑。

```sh
# 检查正式运行目录模块；只运行该crate的库测试。
cargo test --manifest-path codex-rs/Cargo.toml --locked --offline -p codex-uds --lib

# 在上述 harness 目录布局下运行真实生产别名模块的回归。
cargo test --manifest-path .harmony-build/runtime-profile-tests/alias-harness/Cargo.toml --locked --offline --lib
```

目标验证程序被安装为同包 `bin/codex`，编译时绑定本次应用 UID 与同批已签入口的 SHA256；只有正常应用内 `posix_spawn` 启动，才有相符的应用上下文。不能把它从 HDC 直接执行的结果混作 HNP 验收。
