# 应用宿主权限对照测试报告

测试日期：2026 年 10 月 4 日。设备为 `OpenHarmony-7.0.0.105 / 2in1 / aarch64` 模拟器，HDC 目标 `127.0.0.1:5555`。原型包名 `com.codex.emulatorhost`，应用 UID/GID `20020058`，只声明普通 `ohos.permission.INTERNET`。

**结论：官方普通原生子进程可以运行正常打包的共享库，并具备网络、私有文件、管道、PTY 和系统 Shell 基础能力；从应用数据目录启动独立自签名 ELF 仍被拒绝。Codex 还存在确定的执行器入口契约阻塞，不能据此宣称完整 CLI 已可用。**

## 测试结果

| 场景 | 方法 | 实测 | 结论 |

| 应用主进程 NAPI 联网 | 固定公开域名 DNS/TCP | DNS=0，TCP 成功 | 通过 |

## 假配置安全通道

本轮夹具只有 `probe_only = true` 和固定模型名，没有地址、Key 或认证字段。

1. 应用在 `Context.filesDir` 下自己创建 `handoff-private`，原生验证所有者为本应用，权限严格为 0700，并拒绝符号链接。
2. 用官方 HDC 调试应用传输功能投递夹具到该目录。传输文件仍为 0660，但其父目录为 0700。
3. 应用通过已验证目录 FD 和 `openat(O_NOFOLLOW)` 读取，只接受固定夹具内容与本应用所有的普通文件。
4. 应用以 `O_CREAT | O_EXCL | O_NOFOLLOW` 创建新文件，mode0600，写入并同步后再次 `fstat`。

实测最终 UID/GID 对应应用，文件 mode0600。此原型只接受假夹具，不是生产配置导入器。正式实现还需原子更新、清理暂存、错误回滚、重放处理、完整父路径与当前 Codex 目录校验，以及禁止日志记录凭据。**不能把真实密钥放进 HAP/rawfile，也不能照搬 HDC 上传后直接充当最终配置。**

## 边界与后续

没有修改系统安全策略、系统目录或用户 HOME，没有启用 full-access，也没有把可执行文件改造成共享库来绕过限制。官方子进程共享库是从 C++ 源码正常编译、随 HAP 打包，由平台接口加载。

普通应用能力不等同于 Codex 的 read-only/workspace-write 隔离语义。这轮没有补齐此前探测缺失的 user namespace/Landlock，没有验证任意开发工具、Codex re-exec 助手、长期后台生命周期或真实模型调用。下一步见 [原生宿主集成方案](原生宿主集成方案.md)。

官方接口依据：[OpenHarmony 原生子进程开发指导](https://raw.githubusercontent.com/openharmony/docs/master/zh-cn/application-dev/application-models/capi-nativechildprocess-development-guideline.md)。本机 SDK API26 的 `AbilityKit/native_child_process.h` 和 `PermissionDefinitions.json` 也已核对；普通网络权限为 normal/system_grant。
