# 原生宿主集成方案

状态：2026 年 10 月 4 日，基础能力已实测，Codex 集成尚未实现。本文的结论区分本机实测、源码约束和未满足的外部前提。

## 已经成立的路线

官方 `OH_Ability_StartNativeChildProcess` 可以让普通 HAP 创建 `NORMAL` 原生子进程，加载随包正常编译的 `.so` 并传递参数、文件描述符。本机仅申请 `INTERNET` 就完成了 DNS/TCP、私有文件、管道、PTY、系统 Shell 和短时存活测试。因此可以继续研究把 Rust 功能编译成真正的 `cdylib`，由一个明确的 C ABI 入口调用；不用改已有 ELF 的类型，也不用从数据目录强行执行程序。[官方原生子进程指导](https://raw.githubusercontent.com/openharmony/docs/master/zh-cn/application-dev/application-models/capi-nativechildprocess-development-guideline.md)

**这条路线解决了原生代码的正规宿主，尚未解决当前 Codex 的自执行助手契约和工具沙箱。不能直接把现有 CLI 放进共享库后认为工作完成。**

## 当前不能直接调用 `codex_exec::run_main`

| 源码位置 | 已确认行为 | 集成影响 |
| --- | --- | --- |
| `codex-rs/arg0/src/lib.rs`，`Arg0DispatchPaths` | 路径字段形式上是 `Option<PathBuf>` | 不代表下游允许缺失 |
| `codex-rs/exec/src/lib.rs`，`run_main` | 无条件构造 `ExecServerRuntimeOptions::from_optional_paths` | 纯问候也会走该检查 |
| `codex-rs/exec-server/src/runtime_options.rs` | 没有真实 `codex_self_exe` 就返回 `Codex executable path is not configured` | `Arg0DispatchPaths::default()` 不可用 |
| `codex-rs/exec-server/src/environment.rs`，`from_snapshot` | 默认本地环境必须有 runtime paths | 只跳过第一处检查仍会失败 |
| `codex-rs/exec-server/src/process_sandbox.rs` | 使用真实 Codex 路径启动隐藏执行助手 | `.so` 路径不能替代可执行程序 |
| `codex-rs/exec-server/src/fs_sandbox.rs` | 文件工具通过真实 Codex 路径启动文件助手 | 文件写入、受限读取也需要完整后端 |
| `codex-rs/exec/src/lib.rs`，`read_prompt_from_stdin` | 非TTY输入即使已有提示词，也可能读取至EOF | 未关闭的管道会让纯问候挂起 |

不能把系统孵化器、缺失路径、假文件或共享库路径作为 `codex_self_exe`。`Environment::default_for_tests()` 明确创建无沙箱本地后端，也不能用来绕过生产执行器契约。

`codex_exec::run_main` 使用进程内 app-server 客户端，纯非交互路径不要求先启动独立 daemon 的 socket listener。直接进入库函数也不会自动调用 CLI 的 `arg0_dispatch()` 创建 PATH aliases；但这仅避免无关启动入口，不能省掉它们背后真实助手所需的能力。已有目录所有者、父路径、符号链接与权限校验继续保留。

当前决定：**暂不通过新建“聊天专用”生产分支绕过这些检查。先确定正规的真实助手打包与执行路线。**

## 完整集成需要的改动

1. **Rust 入口与生命周期。** 新建真正的 `cdylib` crate，显式导出 C ABI；校验参数长度与命名FD；限制一次子进程只启动一次运行时。按仓库 `codex-async-utils` 的16MiB栈预算创建工作线程和Tokio worker；FFI边界处理panic。CLI的进程退出只结束该子进程；HAP界面能够感知结束，不能把UI进程内NAPI调用当CLI主进程。
2. **Context与文件。** 由应用取得真实 `Context.filesDir/cacheDir/tempDir`，通过参数/FD传给子进程；在子进程开始业务线程前配置自己的 `HOME/CODEX_HOME/TMPDIR/cwd`。父进程资源和环境不能假设自动继承。目录要实际通过当前Codex检查，不能因本轮C探针可以写就删除安全校验。
3. **标准输入输出。** 非交互问候将stdin绑定到明确EOF的管道或合法打开的空输入，stdout/stderr绑定到命名FD。读写双向TTY时另外实现主从端、窗口尺寸、终止与回收。本轮只验证PTY基本读写，尚未测完整TUI。
4. **真实自执行助手。** 先评估私有HNP能否正常安装并启动真正的Codex助手，然后才填入其已验证路径。必须支持执行助手、文件助手、apply-patch入口、sandbox helper及相应资源发现。不能把系统Shell成功当作这些助手也成功。
5. **官方子进程后端候选。** 若选择将助手也编译为正常`.so`入口，需要显式改造执行器后端与IPC协议。官方API对“在子进程再创建子进程”有约束；不能假定Codex所在的Native子进程能继续直接调用同一创建API。可能需要主应用负责创建，但主应用必须校验请求、工作目录、继承FD和权限策略，不能变成无限制命令代理。这是后续设计工作，未实现。
6. **受限工具策略。** `NORMAL`是系统应用沙箱共享方式，不是Codex的read-only/workspace-write后端。缺少user namespace/Landlock的问题不会因HAP宿主消失；需要有真实隔离的替代后端，无法满足时明确拒绝。不得静默切full-access。
7. **配置导入。** 使用已验证的HDC调试应用传输及应用0700投递目录，应用校验后创建0600最终文件。生产导入另需原子替换、清理、失败回滚与秘密保护。不得把配置/密钥加入HAP、rawfile、编译日志或命令行。

后续首次真实请求仍限定 `gpt-5.6-terra`、read-only、一次纯问候。它只在入口、真实助手契约和配置安全通道成立后执行；本轮没有发送这个请求。提示词中“不要使用工具”不能替代后端能力或权限控制。

## HNP 的只读核查

HNP是官方Native软件打包方案：原生二进制及依赖打成`.hnp`，再进入HAP，随HAP安装、签名和分发。官方文档还给出应用使用`execv/execve`调用已安装Native包的方式，私有HNP只向安装它的应用开放。这与把rawfile释放到可写数据目录是不同的正常安装路径。[官方Native软件包开发指南](https://raw.githubusercontent.com/openharmony/startup_appspawn/master/service/hnp/README_zh.md)

当前本机SDK确有`toolchains/hnpcli`。打包工具能够生成HNP，只证明工具链存在；尚未构建、签名或安装HNP测试包。官方流程要求HAP签名信息，包含相应证书和Profile；本轮unsigned模拟器原型不能代替这项验证。商业HarmonyOS PC是否接受所持证书、Profile与包权限，还需要合法的调试/发布材料和实测。[官方应用与二进制签名工具](https://raw.githubusercontent.com/openharmony/developtools_hapsigner/master/README_ZH.md)

本机API26权限定义摘录：

| 权限 | 等级 | 授权类型 | 判断 |
| --- | --- | --- | --- |
| `INTERNET` | normal | system_grant | 本轮应用已经使用 |
| `INHERIT_PARENT_PERMISSION` | normal | system_grant | SDK中存在，限定2in1；未测试HNP继承 |
| `CUSTOM_SANDBOX` | system_basic | system_grant | 不是普通应用随意声明即可获得 |
| `ALLOW_EXTERNAL_NATIVE_CODE` | system_basic | system_grant | SDK中限定2in1；未申请、未测试 |

依据为SDK的 `openharmony/toolchains/lib/PermissionDefinitions.json`。后两项的 `provisionEnable=true`，继承父权限项为false；不能把定义存在等同于已经授权。

已读官方HNP开发指南没有写“所有私有HNP一律需要system_basic”，因此不能给出这个断言；也不能由“文档没写”推导普通权限必然能跑Codex及所有工具。对于外部原生代码、弱沙箱或额外系统调用确实需要的受限权限，应按官方审核/授权流程取得，作为外部前提，不修改SDK授权模板或系统策略来代替授权。

ELF本机自签名与权限签名也不同：本次SDK自签日志明确跳过`.profile/.permission`，不能因此给子程序推定INTERNET或父权限继承。后续只能用官方签名和打包流程；不修改ELF格式、伪造权限或自己补段规避校验。

## 下一阶段的验收顺序

| 顺序 | 工作 | 通过条件 |
| --- | --- | --- |
| 1 | 合法私有HNP小探针 | 正确签名安装、普通`exec`成功、子程序实际网络身份与权限确认 |
| 2 | 真实Codex助手路径 | 路径/摘要/包来源可核验，隐藏助手各自冒烟通过 |
| 3 | Rust官方宿主入口 | `cdylib`正常加载、16MiB栈、退出回收与stdin EOF通过 |
| 4 | 现有目录与策略 | 应用Context下通过现有校验，符号链接/错误UID负例仍拒绝 |
| 5 | 一次只读问候 | 固定模型、不切权限、真实TLS与API通过、无秘密日志 |
| 6 | 完整工具能力 | 文件、命令、PTY、取消、超时、隔离负例及重启恢复逐项报告 |

第1项若证书或平台授权不满足，则记录外部前提并停止依赖步骤；不能把前面的C探针通过升级成“完整Codex已跑通”。
