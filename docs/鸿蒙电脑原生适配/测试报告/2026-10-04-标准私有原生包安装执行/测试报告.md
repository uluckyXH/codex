# 标准私有原生包安装执行实验报告

日期：2026-10-04。该报告独立记录 HNP 路线，未覆盖此前数据目录 ELF 执行失败的证据。本报告保留各轮实验先后顺序与原始失败；完整包结果在末尾追加。

## 结论

在当前 HarmonyOS 7.0.0.105、2in1、aarch64 模拟器中，官方私有 HNP → 普通调试 HAP → 应用中正常 posix_spawn 的路径可用。HAP 只声明 INTERNET，没有增加系统级权限；模拟器接受未签名 debug HAP。HNP 中原始 SDK 自签 network-probe 执行成功、退出 0，并成功完成 developer.huawei.com:443 的 DNS 与四个 IPv4 TCP 连接。安装后回读的 ELF 与原始文件 SHA-256 完全一致。

首轮证明存在正常原生可执行程序的承载路径。当时尚未测试完整 Codex；后续已推进到完整包和只读模型问候，见末尾追加结果。受限工具沙箱、正式签名 HAP 和零售真机仍须分别验证。

## 实验方法

- 独立项目：`.harmony-build/emulator-hnp`；独立包名：`com.codex.emulatorhnp`，实测 UID/GID 均为 20020059。
- SDK 工具：`hnpcli pack` 生成 `codexnetprobe.hnp`；`app_packing_tool.jar --mode hap --hnp-path` 正常打入 HAP；`hdc -t 127.0.0.1:5555 install` 安装。
- `module.json5`：`hnpPackages` 中声明 `private`、`independentSign: false`；权限列表仅 `ohos.permission.INTERNET`。
- ELF 沿用上轮原文件；没有修改 ELF 格式或权限节。用于目录诊断的第二个 ELF 以 SDK clang 正常构建，并用 `binary-sign-tool.jar sign -selfSign 1` 正常签名；签名日志明确未写入 `.profile` 或 `.permission`。
- 本报告作者的探针没有读取真实 config.toml、Key 或自定义接口，也没有发模型请求；后续主会话单独验证了真实接口。整个流程没有 root、修改 SELinux、全局 chmod 或更改系统策略。

## 文件工具回归中的失败与更正

### umask的实际边界

NAPI初始化对本应用进程调用umask(0077)，测试原生openat请求0666，观测结果仍然0666；apply_patch普通文件也为0666。因此本平台下不能仅依赖umask推定文件最终权限。本报告将这一检查如实保留为未达到0600预期，未用工作文件的内容通过替代权限结论。

配置导入器以及宿主stdout/stderr/status均显式创建0600文件并校验，相关目标测试通过；所有fixture与应用state父目录均0700。这里的“日志0600”仅指宿主创建的这些日志，不推断上游codex-tui.log的权限。
