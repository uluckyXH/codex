## SDK 评估与 Shell 源码改动

当前 SDK 的 `spawn.h` 没有声明 `posix_spawn_file_actions_addchdir_np` / `addfchdir_np`，aarch64 SDK libc 的导出符号也没有这两个函数或 spawn umask 属性，见[只读符号检查](SDK-spawn导出符号.txt)。没有自行补声明、依赖未提供的符号，也没有修改宿主进程的 cwd/umask。

Shell 分支直接 `posix_spawn("/system/bin/sh", ...)`，argv为 `sh -i -s`。同一 Shell 的私有 `ENV` 初始化文件只执行内建操作：umask077、核对并切换专用 `CODEX_TERMINAL_CWD` 环境值、清除两个初始化环境变量、向独立fd3管道发送回执、关闭fd3。cwd为结构化环境值，带中文、空格、引号或命令替换字符也不会拼接进脚本文本。`exec 3>&-` 仅执行重定向，不再执行第二个 Shell 可执行文件。

初始化文件位于已验证的 `host/control`，名称含随机会话token，使用O_EXCL/O_NOFOLLOW/CLOEXEC和0600，并检查实际owner、类型、链接数及模式。回执管道与PTY输入分离，宿主两端FD均至少10，子进程只保留回执fd3；等待最多三秒。拿到完整回执后才返回启动成功并按已固定文件身份删除初始化文件；回执缺失/错误会进入既有有限停止流程。未确认的进程及PTY状态不会被覆盖。Shell real/effective UID 或 real/effective GID 不一致时拒绝此初始化方式，不借改变身份使启动文件生效；没有比较UID与GID是否相等。

新会话仍在setsid后打开本次slave并复制到标准0/1/2，保留既有signal mask/default、尺寸、termios及稳定进程句柄要求。Codex分支原有固定bootstrap、参数及策略保持原样。

OpenHarmony 的 mksh 源码在非特权交互模式下读取 `ENV` 初始化文件，之后才进入标准输入命令循环；`-s`指定从标准输入读取命令。[OpenHarmony main.c](https://github.com/openharmony/third_party_mksh/blob/master/main.c)，[OpenHarmony mksh 手册](https://github.com/openharmony/third_party_mksh/blob/master/mksh.1)。这提供了采用该机制的源码依据，并不代替当前设备验证。

## 已知 leader 与枚举对照

`OwnedProcesses::Observe` 在全局枚举前直接读取已pin的leader，并核对PID/starttime、session、实际real/effective/saved UID和 `waitid(WNOWAIT)` 归属。枚举中的同PID记录必须与直接记录一致；leader未出现时，可以把经验证的直接记录加入父子/session图，继续观察运行中的会话，不再仅因集合缺少leader返回旧的ESTALE。

新增 `process_scan_anchor` 对照日志包含 `enumerated=0/1`、expected/actual start、group、sid、三种实际UID及wait_owned。直接读取或二次重验失败仍保留具体阶段和PID。成功对照的日志只在内容变化时写入，不每次扫描刷屏。

没有把看不见的进程当成已死：已pin后代仍按pidfd统计存活；身份不明/已受管的不可读项仍失败，最终仍重验直接leader和等待归属。若leader已退出但依旧不出现在枚举中，本轮扫描返回 `proc_visibility_unverified`，不据此认证所有不可见后代已清理；五秒后暂停的既有未确认流程仍保留。主会话已观察到退出后枚举恢复，因此下一轮应核对实际 `enumerated` 变化和最终成功顺序，不能预先假设一定恢复。
