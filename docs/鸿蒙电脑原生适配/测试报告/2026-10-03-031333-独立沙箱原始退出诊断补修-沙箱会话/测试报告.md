这 1 项是仓库 cli/src/debug_sandbox/exit_status_tests.rs 中的回归测试。本批用《standalone_host_entry.py》原样提取生产处理函数，并引用原来的 cli/exit_status.rs、utils/pty/diagnostics.rs 和同一测试模块编译独立 Rust harness。入口同时断言两个实际调用点都接入处理函数；来源与 hash 见《宿主入口摘要.json》。这不是完整 CLI 的 cargo test 或实际沙箱端到端运行，也不加载 Config、用户配置或认证。两个被过滤项是所引用格式化模块的既有测试，不计入本轮覆盖。

OHOS 检查针对实际 CLI 库及依赖，不以独立 harness 替代目标类型检查。新入口复用既有 describe_exit_status，因此将 CLI 原有 codex-utils-pty 从开发依赖移动到普通依赖；根 Cargo.toml/Cargo.lock 未变。此次没有新增外部符号或更换依赖版本，未重复完整 release 或目标测试链接；完整发布链接由主会话接手。

## 诊断语义

两个既有退出调用点统一到 handle_debug_sandbox_exit_status。仅 CODEX_HARMONY_PROCESS_DIAGNOSTICS=1 时，在原 handle_exit_status 之前输出 stage=debug-sandbox-wait、当前 PID 以及已有格式化器生成的 code/signal/raw_wait_status/core_dumped。随后调用原退出函数：显式 159 仍返回 159，TERM 仍返回 143。权限选择、执行命令、登录和错误传播没有改变；原始信号不被解释成 SIGSYS 或 seccomp。

脚本的 stderr 重定向可采集新增诊断行，脚本本身未修改。此改动能区分已等待到的子进程结果，不能保证取得在 CLI 启动或主进程提前终止之前尚未产生的状态。
