## 修改与接口

本轮生产修改仅 `owned_processes.h`、`owned_processes.cpp`、`pty_session.cpp`。保留 Shell 直接启动、私有 ENV 初始化、termios、会话 token、输入上限和既有停止期限。

新增 `bool OwnedProcesses::ObserveRunning(std::string &diagnostic, bool &complete)`。返回 true 表示运行期可继续使用；只有 complete=true 表示严格扫描成功。complete=false 时 diagnostic 与 errno 保留扫描失败原因，不能用返回 true 推定 cleanup 完成。既有 `Observe(std::string &error)` 签名不变，继续表示严格扫描；`codex_launcher.cpp` 无需接口修改，仍调用该严格接口。无需 ArkTS/NAPI 签名调整。

运行期扫描不可用时，必须存在启动时已核对 UID/start/session 的 leader pidfd；同一 pidfd 的两次非阻塞 poll 包围 `waitid(P_PID, WEXITED|WNOHANG|WNOWAIT)`。只有句柄无退出/错误事件、wait 归属有效且无退出通知，才继续保持 running。不会为此重新打开 leader 数字 PID 的句柄。身份变化、缺少锚点、丢失 wait 归属、poll 错误或已退出均不能降为可见性诊断。

PTY JSON 增加 `procVisibilityUnknown`、`procScanErrno`；运行期部分视图不设置 error 或 cleanupUnknown，因此不再因 proc 不可读显示 stop_failed。去重日志阶段为 `process_scan_unverified_running`，保留 cause、pidfd_alive、wait_owned、proc_complete。部分视图按500ms观察；恢复完整视图有恢复记录。

暂停中的直接子进程仍为存活：WEXITED 不消费停止/继续事件，pidfd 无退出事件。输入继续使用64KiB有界队列和非阻塞 PTY；真正退出后立即清空输入，进入停止流程。没有增加自动 SIGCONT 或信号数字 PID 的路径。

开始关闭或观察到自然退出后，PTY 只调用严格 Observe。信号仅发给此前完成身份核对并保留的稳定句柄。退出后再次枚举，必须重新读取并枚举到未回收 leader，确认所有已固定成员均已退出，再做最终新扫描、waitpid 和 PTY 释放。过滤的枚举、不可读活成员、wait/poll 失败均保留未确认；五秒后暂停，显式重试规则不变。

ENOENT 不再直接等于死亡：已有句柄或临时 pidfd 必须证实退出，才能跳过元数据缺失的枚举项。临时句柄只用于判断是否消失，永不加入 tracked、永不发信号；旧已退出句柄也不能证明同数字 PID 的新占用者死亡。Pin 的二次元数据读取失败亦需句柄证实退出才能跳过；Begin 必须实际保有 leader pin 并验证 wait 归属才能成功。

本机制仍管理会话和已观察后代，不承诺隔离未观察、脱离会话的双重 fork 守护进程。一次成功枚举不是系统不存在任何隐藏进程的证明；本轮没有放宽该边界。

pidfd 的退出可读事件与子进程 wait 用法依据 [Linux pidfd_open 文档](https://man7.org/linux/man-pages/man2/pidfd_open.2.html)，WNOWAIT/状态筛选依据 [waitid 文档](https://man7.org/linux/man-pages/man2/waitpid.2.html)。当前商业鸿蒙设备行为仍需主会话用最终 HAP 验证。

## umask 补记

主会话的 chmod600 后 stat600 成功，削弱了“固定把文件模式显示666”的解释。此前 native openat(O_CREAT|O_EXCL,0666)+fstat 已复现666，因此不是 Shell 重定向或 toybox stat 独有。公开 OpenHarmony [toybox mkdir 源码](https://raw.githubusercontent.com/openharmony/third_party_toybox/master/toys/posix/mkdir.c) 在用户态先按 old_umask 计算目录请求模式，故目录700本身不能证明内核已掩蔽文件模式。默认 ACL 是可以同时解释文件666与目录700的候选：[umask 规则](https://man7.org/linux/man-pages/man2/umask.2.html) 与 [OpenHarmony posix_acl_create](https://raw.githubusercontent.com/openharmony/kernel_linux_5.10/master/fs/posix_acl.c) 都区分默认ACL继承和 umask；尚无本设备 ACL 证据，不能认定根因。本轮未为此改业务或执行额外设备检查。
