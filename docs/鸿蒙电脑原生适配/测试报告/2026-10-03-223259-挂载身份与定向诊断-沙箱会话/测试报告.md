## 证据与取舍

输入只有[真机汇总](../../../鸿蒙Codex-g913098105a40-真机复测报告.txt)、[补充材料清单](../../挂载识别故障补充材料清单.md)与[主计划](../../挂载识别与探针退出修复计划.md)。没有收到完整原始日志、失败 Rust 进程的 metadata 或完整挂载表。测试中的 3996、66699、362362、20020101 均为采用报告数值构造的合成输入，不是现场重放。

SDK 与 Rust 的 major/minor 采用相同编码规则，替换宏不能解决假设中的编码不一致。本次 OHOS 分支使用同一目录 FD 的 statx 明确设备号，并要求 TYPE、MODE、UID、GID、INO、MNT_ID 字段有效；目录类型、权限、UID/GID、inode 与 Rust metadata 相同，正的 mount ID 与同 FD 的 fdinfo 一致，采样前后挂载命名空间相同。缺字段、错误或冲突均拒绝。然后要求完整 mountinfo 的唯一 ID 条目与明确设备号精确匹配，继续原有可见性、覆盖、别名、直接绑定和嵌套检查。没有 hmfs 名称特例或产品代码中的历史 dev/mount ID 常量。

[statx 接口说明](https://man7.org/linux/man-pages/man2/statx.2.html)定义明确设备号及与 mountinfo 对应的普通 MNT_ID；设备字段没有独立有效位。[Linux stat 实现](https://raw.githubusercontent.com/torvalds/linux/master/fs/stat.c)和[挂载表实现](https://raw.githubusercontent.com/torvalds/linux/master/fs/proc_namespace.c)支持使用显式主次编号这一来源选择，但它们不是商业鸿蒙内核的现场证据。实际 SDK/Rust 结构与接口见 [摘录](SDK与Rust接口摘录.txt)；[C 编译断言](目标字段布局核对.c)核对 statx 大小、关键偏移和 mask。SDK `sys/stat.h` 未提供本次可见的 statx 声明，代码继续使用已有 rustix 接口；[构建配置](编译包装器与Rustix后端.json)确认本批 rustix 选用 `linux_raw` 后端。

此选择会拒绝缺少 statx 身份字段、fdinfo 或命名空间读取能力的 OHOS 环境，即使传统设备解码曾可能匹配。该收紧用于避免在身份来源不完整时放行；是否适合商业 PC 的实际内核必须通过新包日志确认。其他 Linux 保留传统 dev 解码和 Btrfs 设备差异例外，但本初版额外查询 statx 的问题仍需后续提交。

## 诊断与拒绝分支

显式 `CODEX_HARMONY_PROCESS_DIAGNOSTICS=1` 输出 `[codex-mount] pid=… purpose=aliases|control-sockets stage=…`。记录同 FD 的 metadata dev 原值/十六进制/解码值、inode、owner/mode、fdinfo、statx 请求与返回 mask、明确设备号及 mount ID、fstatfs、命名空间、匹配条目和判定结果。没有开关也返回 purpose、路径和具体 reason。

mountinfo 接受上限 1 MiB，fdinfo 接受上限 64 KiB；实际读取最多上限加一个探测字节。超限明确拒绝，不能用截断前缀判断安全。日志按每 1024 个原始字节分块，记录偏移，字节使用 ASCII 转义，具备 begin/end、captured_bytes、truncated；每条均以同一前缀开始。只读取本进程的相关 `/proc` 信息，不读取配置正文、认证、全部环境或模型内容。
