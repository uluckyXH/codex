# 官方应用权限与签名机制调查报告

日期：2026 年 10 月 4 日。对象：当前运行的鸿蒙 7 电脑模拟器、DevEco Studio 26.0.0 SDK，以及本仓库的原生 ELF 交付路线。

本报告记录只读调查和已有探针结果，不把资料推论写成修复通过。没有修改 SELinux、系统账户、全局目录权限、正式运行模式或现有签名产物；没有读取、输出接口地址和密钥。

## 结论

当前 HDC 调试身份能创建私有目录、启动签名 ELF，但这些能力不足以证明能联网或创建控制套接字。已有探针将失败定位到 TCP `connect` 和 Unix pathname socket `bind`，均返回 `EACCES`（13）。本轮没有取得对应系统审计记录，不能把具体拒绝规则视为已经确证。

SDK 的 `-selfSign 1` 模式明确不写入权限声明。补上 `-moduleFile` 参数也不会改变这一点。证书签名、运行时权限、SELinux 域、用户目录权限、Codex 工具沙箱是不同的检查层，不能互相替代。

官方普通应用可声明 `ohos.permission.INTERNET`。下一步应在这个正常授权的应用上下文中，分别验证应用自身、原生子进程及 Codex。结果应与 HDC shell 的结果分开记录，不能将模拟器调试身份当作正式 PC 的 HiShell 身份。

## 自签名与权限段

本机使用的工具位于 `DevEco-Studio.app/Contents/sdk/default/openharmony/toolchains/lib/binary-sign-tool.jar`。帮助输出包括 `-moduleFile` 与 `-selfSign`，但参数存在不表示所有组合都生效。

本机 `SignElf.writeOptionalSections` 字节码与[官方签名工具源码](https://github.com/openharmony/developtools_hapsigner/blob/master/binary_sign_tool/java/binary_sign_tool_lib/src/main/java/com/ohos/hapsigntool/hap/sign/SignElf.java)一致：自签名分支先返回；只有非自签名分支才写入权限内容。当前仓库自签名调用没有写入权限段。

官方独立二进制授权方式使用真实证书及配套密钥库，通过 `-moduleFile permissions.json -selfSign 0` 签名。所需证书不能用任意生成的证书冒充系统认可的发布证书。[二进制签名工具](https://developer.huawei.com/consumer/cn/doc/doccenter-capabilities/binary-sign-tool.md)和[申请二进制证书](https://developer.huawei.com/consumer/cn/doc/app/agc-help-binary-cert-0000002408063605)说明了入口及材料。

以下是官方权限策略格式的最小联网示例，不表示本次已完成证书申请或在设备验证通过：

```json
{
  "requestPermissions": [
    { "name": "ohos.permission.INTERNET" }
  ]
}
```

权限段应在签名前处理；不能修改已签名 ELF 后继续声称原签名有效。本轮没有重新签名已有产物，也没有改造签名工具以绕过其自签名边界。

## API 26 变更的适用范围

华为官方 API 26 行为变更说明针对以下组合：ROM 7、应用 `targetSdkVersion >= 26.0.0`、应用启动独立 bin、bin 需要名称带 `.kernel` 的权限。此时 bin 不再自动继承父应用的这类权限，应为 bin 声明并签名。没有使用这些权限的应用，不能仅因升级 API 26 就断言受此变更影响。[官方权限策略变更说明](https://developer.huawei.com/consumer/cn/doc/doccenter-release-notes/changelogs-for-all-apps-7001.md)

该说明区分两条打包路线：HNP 使用 `independentSign: true`、给 bin 加入 `.permission` 后重新打包；非 HNP 使用二进制证书签名的 `-moduleFile`。独立授权时，需要的普通权限也必须列入策略。

`ohos.permission.INHERIT_PARENT_PERMISSION` 从 API 23 开始提供，支持 PC/2in1，仅供二进制继承父进程权限。它不能凭空授予父进程没有的能力。本项目应优先明确实际需要的权限，而非将继承全部父权限当作通用修复。[官方权限定义](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/security/AccessToken/permissions-for-all.md#ohospermissioninherit_parent_permission)

本次 `connect EACCES` 尚不能直接归因于 API 26 的 kernelpermission 变化。尤其 `INTERNET` 本身不包含 `.kernel`，需要结合运行身份及当前系统策略继续验证。

## HDC 与 SELinux 的源码证据

上游 HDC 的 `InitShell` 解析 `-b` 后，将 bundle 的调试挂载目录写入 `optionPath`；子进程执行 `chdir` 后 `execl`。沿 `CheckBundlePath`、`ShellFork` 和 `ChildForkDo` 调用链，没有设置目标应用 AccessToken 的步骤。这是源码证据，不是只根据 UID 相同作出的判断；厂商镜像仍需实测核对。[HDC shell 实现](https://github.com/openharmony/developtools_hdc/blob/master/src/daemon/shell.cpp)、[调试目录检查](https://github.com/openharmony/developtools_hdc/blob/master/src/daemon/daemon_base.cpp)

上游 `hdcd.cfg` 未在 permission 数组声明 `INTERNET`，但另有网络相关组和 SELinux 规则。当前设备对应配置文件读取被拒绝，因此不能用上游列表替代该镜像实际权限检查，也不能据此断言 HDC 守护进程不能联网。[HDC 服务配置](https://github.com/openharmony/developtools_hdc/blob/master/src/daemon/etc/hdcd.cfg)

上游 `sh.te` 中，`sh` 的 Unix stream socket 规则未列出 `bind`，临时目录创建规则只列目录和普通文件；同文件也未给出 TCP 连接授权。`hdcd.te` 则明确包含 TCP 连接规则。该差异与已有失败位置一致，但完整策略还可能包含其他属性规则或厂商扩展，不能只凭单个文件的缺项确定实际裁决。[shell 策略](https://github.com/openharmony/security_selinux_adapter/blob/master/sepolicy/ohos_policy/developtools/hdc/system/sh.te)、[hdcd 策略](https://github.com/openharmony/security_selinux_adapter/blob/master/sepolicy/ohos_policy/developtools/hdc/system/hdcd.te)

应继续保留 `EACCES`，通过受支持的应用身份验证，不通过关闭 SELinux、修改系统策略或全局放宽目录权限处理。

## 普通应用和原生子进程路线

`INTERNET` 的权限级别为 `normal`、授权方式为 `system_grant`。普通应用在模块声明后通过正常安装获得，无需为了普通联网能力申请系统应用身份。[官方权限列表](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/security/AccessToken/permissions-for-all.md#ohospermissioninternet)

本机 SDK 的 `AbilityKit/native_child_process.h` 明确区分普通和隔离模式：`NCP_ISOLATION_MODE_NORMAL` 与父进程共享沙箱或网络；隔离模式不共享。`OH_Ability_StartNativeChildProcess` 接收 `libEntry.so:Main` 类型入口，并非直接接收任意 CLI 路径；这个 API 不能在未经适配和测试时当成 `execve(codex)` 的替代品。[官方原生子进程 API](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-ability-kit/capi-native-child-process-h.md)

## 后续验收顺序

1. 普通 HAP 仅声明必要 `INTERNET`，在真实应用进程中记录 UID、网络探针结果和 Context 目录；不记录接口凭据。
2. 使用同一公开端点，比较普通 HDC、`hdc shell -b` 和应用进程，确认系统上下文差异。
3. 单独测试应用正常创建的原生子进程，记录执行成功、目录写入和联网三个结果，不将 `posix_spawn` 成功等同于权限完整继承。
4. 只在上述身份和目录契约得到证据后集成 Codex，模型仍限定为 `gpt-5.6-terra`。
5. Codex 对话、Unix 控制套接字、受限工具执行分别验收。普通联网成功不代表模型工具沙箱支持；纯问候成功也不代表文件操作已经可用。
