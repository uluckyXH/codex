# 鸿蒙 7 电脑模拟器沙箱能力与前置修复测试报告

## 本次结论

已修复一个确定的 bwrap 兼容问题：非特权运行不再读取不会使用的 `overflowuid/overflowgid`。签名版 `bwrap --help` 在模拟器实际返回 0。

**受限执行仍不可用。** 当前模拟器调试身份下，`clone/unshare(CLONE_NEWUSER)` 返回 `EINVAL (22)`，用户 namespace 的 `/proc` 接口不存在；Landlock ABI 查询返回 `ENOSYS (38)`。修复后的 bwrap 正确报告 namespace 能力不足并返回 1，测试命令未执行。seccomp 安装和拦截探针成功，但不等于已具备按项目目录限定读写的完整沙箱。

## 环境与安全边界

- 宿主：macOS 27.0.1 arm64；Python 3.14.7；Rust/Cargo 1.95.0。
- SDK：DevEco Studio 所带 Native 26.0.0.105 / API 26，Clang 15.0.4，目标 `aarch64-unknown-linux-ohos`。
- bwrap：`--locked --release` 的真实 Cargo 目标构建，使用已校验的 OHOS 静态 libcap；没有启用 setuid。
- 签名：SDK `binary-sign-tool.jar sign -selfSign 1`，随后 `display-sign` 检查。
- 设备：hdc `127.0.0.1:5555`，`u:r:sh:s0`，UID/GID 2000，初始进程 `NoNewPrivs=0`、`Seccomp=0`，有效 capabilities 为 0。
- 所有写入仅限新建 `/data/local/tmp/codex-emulator/sandbox-agent`；未修改系统权限、SELinux、内核参数或用户配置；没有读取 URL、Key 或发送模型请求。
- 每项系统调用探针在独立 fork 子进程运行。seccomp 探针只给该子进程安装更严格的过滤器，验证 `getpid` 被拒绝，退出后不影响其他进程。

## 代码修复依据

源码中的 `overflow_uid` 和 `overflow_gid` 仅在 `write_uid_gid_map(..., map_root=true)` 时使用。唯一传入可能为真的调用位于 `is_privileged` 的 setuid 父进程分支；非特权分支及二层 user namespace 分支都明确传入 `false`。

因此将 `read_overflowids()` 限制在 `is_privileged` 分支，不填造默认 ID，不放松 UID 映射或 namespace 检查，也不改变特权模式仍必须读取真实内核值的要求。

OHOS 创建 namespace 返回 EINVAL/EPERM 时，错误信息现在说明当前环境不支持或不允许所需能力，且受限命令没有执行。其他平台保留上游说明。不会自动切换为完全权限。

## 目标运行结果

| 探针 / 用例 | 实际结果 | 解释 |
| --- | --- | --- |
| 内置 `unshare` | 127，`toybox: Unknown command unshare` | 路径存在不能证明命令可用，因此改用原生 C 探针 |
| `unshare(0)`、普通 `clone(SIGCHLD)` | 成功 | 普通进程能力基线正常 |
| `unshare(CLONE_NEWUSER)` | -1 / EINVAL 22 | 当前环境无法创建 user namespace |
| `clone(CLONE_NEWUSER)` | -1 / EINVAL 22 | 与 unshare 结果一致 |
| `unshare/clone(USER \| MOUNT)` | -1 / EINVAL 22 | bwrap 所需组合不可用 |
| 独立 mount/net/pid namespace | -1 / EPERM 1 | 当前非特权身份不允许创建 |
| `/proc/self/ns/user`、`uid_map`、`gid_map` | ENOENT | 与 user namespace 不可用的系统调用结果相互印证 |
| `PR_SET_NO_NEW_PRIVS` | 0 | 可对自身收紧权限 |
| seccomp 安装 | 0 | 过滤器可安装 |
| 被过滤的 `getpid` | -1 / EPERM 1 | 拦截实际生效 |
| Landlock ABI 查询（syscall 444） | -1 / ENOSYS 38 | 当前环境未提供此 syscall 能力 |
| 修复版 `bwrap --help` | 设备退出码 0 | 不再被无用 sysctl 读取阻塞 |
| 修复版受限执行 | 设备退出码 1，namespace EINVAL | 未宣称执行成功 |
| 目标写入命令阻断 | `payload_executed=no` | 沙箱建立失败后没有执行目标命令 |
| 可写目录对照与加强复测 | 普通写入退出 0；加入专用目录可写绑定后，受限执行仍退出 1、标记不存在 | 排除只读根挂载导致无法创建标记的歧义 |

探针子进程均正常返回，无信号终止。探针的退出 0 只表示采集完成，不代表其中各项能力成功。hdc 宿主命令在远端命令失败时也可能返回 0；本报告使用远端显式打印的退出码和探针 `waitpid` 状态判定。

## 复现命令

以下命令均从仓库根目录执行；不要使用现有产物路径重复签名，需为新的复测批次选择新的输出路径。

```sh
# 构建小型原生探针：只依赖目标 libc。
"/Volumes/MacSSD/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/native/llvm/bin/clang" \
  --target=aarch64-linux-ohos \
  --sysroot="/Volumes/MacSSD/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/native/sysroot" \
  -D__MUSL__ -O2 -Wall -Wextra -Werror \
  scripts/harmony_sandbox_probe.c \
  -o .harmony-build/emulator-sandbox/harmony-sandbox-probe-unsigned

# 仅构建受影响的沙箱工具，不构建整个 Codex。
python3 scripts/build_harmony.py build \
  --sdk "/Volumes/MacSSD/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/native" \
  --output-dir .harmony-build/emulator-sandbox/bwrap-build \
  --native-deps ".harmony-build/七版发布/原生资源复测/辅助编译/原生依赖" \
  --package codex-bwrap --release

# 为 bwrap 生成独立签名文件并检查签名；探针使用同样入口。
python3 scripts/sign_harmony.py \
  --sdk "/Volumes/MacSSD/Applications/DevEco-Studio.app/Contents/sdk/default/openharmony/native" \
  --java "/Volumes/MacSSD/Applications/DevEco-Studio.app/Contents/jbr/Contents/Home/bin/java" \
  --input .harmony-build/emulator-sandbox/bwrap-build/target/aarch64-unknown-linux-ohos/release/bwrap \
  --output .harmony-build/emulator-sandbox/bwrap-signed \
  --record .harmony-build/emulator-sandbox/bwrap-signature.json
```

hdc 将签名程序传入上述专用目录后，实际受限用例为：

```sh
# 在设备中执行；目标命令只有在沙箱完整创建后才有机会创建标记。
/data/local/tmp/codex-emulator/sandbox-agent/bwrap-fixed \
  --unshare-user --unshare-pid --die-with-parent \
  --ro-bind / / \
  --bind /data/local/tmp/codex-emulator/sandbox-agent /data/local/tmp/codex-emulator/sandbox-agent \
  --proc /proc --dev /dev -- \
  /system/bin/sh -c 'echo should_not_run >/data/local/tmp/codex-emulator/sandbox-agent/unexpected-writable-payload'
# 必须在目标命令之后立即保存远端状态。
harmony_sandbox_exit=$?
echo "device_bwrap_restricted_exit=$harmony_sandbox_exit"
# 验证失败时目标命令没有实际写入文件。
if test -e /data/local/tmp/codex-emulator/sandbox-agent/unexpected-writable-payload; then
  echo payload_executed=yes
else
  echo payload_executed=no
fi
```

首轮 `restricted.log` 仅使用只读根绑定；其 namespace 错误能定位启动阶段，但“标记不存在”单独不足以证明目标命令未执行。随后在 `restricted-writable.log` 加入专用目录可写绑定，并先用普通 shell 写入 `direct-write-control`（退出 0），完成上表的加强验证。旧日志保留。

原始关键错误：

```text
bwrap: Creating sandbox namespaces failed (EINVAL): this HarmonyOS execution environment may not support the required user namespace. Restricted commands were not run.
device_bwrap_restricted_exit=1
payload_executed=no
```

## 仍需解决的能力边界

换成可写目录可以解决配置或缓存写入，却不能让未提供的 namespace/Landlock 出现。当前结果高度符合此模拟器内核未提供 user namespace 的情况；未读取内核编译配置，不声称已确认具体 `CONFIG_USER_NS` 配置值。`clone(2)` 官方手册列明，不支持所请求的 user namespace 时可以返回 EINVAL。[Linux man-pages](https://man7.org/linux/man-pages/man2/clone.2.html)

seccomp 能过滤系统调用及标量参数，不能直接解引用路径字符串，也不是完整文件沙箱。因此不能以本次 seccomp 成功取代按项目目录执行的隔离保证。[Linux 内核 seccomp 文档](https://docs.kernel.org/userspace-api/seccomp_filter.html)

后续可分别推进普通运行目录和 CLI 交互验证，以及具备正式目录授权、执行身份和策略的鸿蒙宿主方案。华为官方对 IDE 调用签名扩展程序规定了弱沙箱权限和系统设置要求；这说明需要合适的应用执行上下文，不代表自动拥有 Codex 所需的 user namespace。[华为官方 PC 权限说明](https://developer.huawei.com/consumer/cn/doc/doccenter-dev-faq/faqs-access-control-23)

若用户明确选择仅验证完全权限模式，应单独标注其权限边界与结果，不能计为本报告的“受限沙箱通过”。本次没有修改配置为完全权限。
