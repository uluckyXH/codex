状态：覆盖适配14—16，已开始凭据依赖与错误行为适配；网络登录尚未真机验证。系统签名证书与网络 TLS 根证书用途不同，分别按签名专题和本专题处理。

## 可行性与必须保留的能力

用户已明确要求保留账号登录和 API Key 接入，它们属于鸿蒙原生版的核心能力。不能为了先编译通过而删除登录入口、只留下 API Key，或反过来强制所有用户使用 ChatGPT 登录。

从当前源码看，登录依靠网络认证协议和本地凭据存储，不依赖 macOS 的 Codex App。因而有移植到鸿蒙 PC 的技术基础；适配重点是 TLS、浏览器入口、回环网络和存储接口。官方尚未确认鸿蒙 PC 支持，不能据此断言服务端一定拒绝鸿蒙，也不能保证自编译客户端一定获准登录。最终仍须验证实际客户端、账号、工作区权限和网络条件下的完整流程。

程序签名解决鸿蒙是否允许加载本机程序；OpenAI 认证解决账号或 API 凭据是否允许访问服务。取得鸿蒙签名不能代替服务端授权。继续复用上游协议、PKCE、state、客户端配置及刷新逻辑，不伪造其他操作系统身份来声称兼容。

2026-10-02 核对的[官方认证说明（OpenAI Docs）](https://learn.chatgpt.com/docs/auth)确认 CLI 支持 ChatGPT 和 API Key 两类入口，设备码方式需要账号或工作区启用。该说明没有提供鸿蒙 PC 的兼容保证；以下适配安排是本项目的设计。

## 网络与证书怎么适配

先确认 DNS、套接字、线程和事件循环的目标支持，再验证 HTTPS、流式响应、WebSocket、超时、重试和取消。休眠恢复、网络切换、代理失效及系统时钟错误均纳入测试。

根证书加载需要明确来源：优先验证现有系统根证书读取路径；若不可用，设计受维护的根证书来源或复用已有自定义 CA 接口。不能默认商业鸿蒙暴露与 Linux 相同的证书文件布局。

当前自定义 CA 代码读取 `CODEX_CA_CERTIFICATE`，其次读取 `SSL_CERT_FILE`。只有实际需要且来源可信时配置 PEM 文件；先检查格式和可读性，再建立连接。不得通过关闭 TLS 校验解决移植问题。

加密库替换会影响算法支持。例如现有提供方显式检查 ECDSA P-521/SHA-512；若换成另一后端，需验证相同需求，而非只证明一个普通 HTTPS 请求成功。

第一轮构建发现 `native-tls` 需要目标 OpenSSL。现已在 HTTP 模块仅对 OHOS 启用 `vendored`，使用锁文件中的 OpenSSL 源码及鸿蒙 SDK 交叉编译，不链接苹果电脑的 OpenSSL。`codex-http-client` 的 OHOS 目标检查已通过，真实证书来源和网络连接仍待设备验证。

代理支持同时检查主模型请求、登录、WebSocket 和 MCP。保留上游代理及 `NO_PROXY` 语义；系统 GUI 代理能否被终端程序读取需要单独验证，不自动改写用户全局网络设置。

## 登录方式与首轮顺序

| 方式 | 首轮安排 | 鸿蒙相关验证 |
| --- | --- | --- |
| API Key | 首轮独立验收，长期保留 | 标准输入、保存与读取、有效和无效密钥的实际请求 |
| ChatGPT 设备授权 | 首轮优先验证，账号或组织须允许该方式 | 输出 URL/代码、轮询、取消、过期与成功保存 |
| ChatGPT 浏览器与本地回调 | 保留现有入口，设备授权后继续完成 | 手动打开链接、自动唤起、回环监听、端口占用和回调校验 |
| 自定义服务的 API Key | 保留现有提供方配置能力，单独验收 | 服务地址、独立环境变量、协议与模型兼容性 |
| 状态查询、刷新和退出 | 与对应登录方式一起交付 | 新进程读取、ChatGPT token 刷新、失效提示及凭据清理 |

保留上游认证协议，不创建替代登录服务，不把 API Key 与订阅登录的权限或计费混为一谈。设备授权和 API Key 的具体账号可用性由服务端决定。[官方认证说明](https://learn.chatgpt.com/docs/auth)

源码现有命令为 `codex login --device-auth`、从标准输入使用 `codex login --with-api-key`，以及 `codex login status`。首次使用的操作顺序集中在[安装指南](安装配置与运行指南.md)。

浏览器暂时无法自动唤起时，仍可输出登录链接供用户在同一鸿蒙 PC 的浏览器中打开；普通浏览器登录的回调指向该机回环地址，不能把链接直接交给另一台机器并假定回调会返回。设备授权不依赖这个本地浏览器回调，浏览器可只负责授权，Codex 主进程及项目操作继续在鸿蒙 PC 本机运行。

当前 [CLI 登录实现](../../codex-rs/cli/src/login.rs)对显式 `--device-auth` 的失败会直接报错；只有特定的默认登录分支在设备授权返回不支持时转入浏览器流程。鸿蒙方案不能把所有失败一律自动切换，也不能替用户切换成不同计费方式。账号未启用设备码时应给出原因，由用户选择允许的入口。

手动打开链接、设备码和 API Key 可以分阶段验证，但未完成的浏览器体验要保持明确状态，不因此宣称所有登录方式都已适配完成。

## API Key 与自定义服务接入

官方 API Key 继续使用上游标准输入入口：`printenv OPENAI_API_KEY | codex login --with-api-key`。密钥由用户在自己的环境中提供，不内置共享密钥，不要求先登录 ChatGPT。不同登录方式仍受已有的管理员认证限制约束。

当前 `login_with_api_key` 主要把密钥交给存储后端；`codex login status` 的 API Key 分支读取并显示脱敏状态，没有完成模型调用。验收要分开记录：命令接收成功、凭据持久化成功、实际模型请求成功。无效或撤销的 Key、账号权限不足及额度问题必须保留服务端错误，不能用本地保存成功覆盖它们。

API Key 没有 ChatGPT refresh token 的刷新流程。密钥撤销或轮换时，由用户更新密钥并重新验证。ChatGPT 登录则保留上游 token 刷新、失效后重新认证和工作区限制逻辑。两者的权限和计费不互换；API Key 不自动获得 ChatGPT 订阅或云端功能。[官方说明](https://learn.chatgpt.com/docs/auth)

自定义服务继续沿用现有 `model_provider` / `model_providers` 配置：

| 设置 | 保留的含义及验证要求 |
| --- | --- |
| `base_url` | 用户选定的服务地址；校验最终请求实际发往该地址 |
| `env_key` | 从指定环境变量读取该服务的 Key，不把密钥值写入配置样例 |
| `requires_openai_auth` | 保留上游认证选择逻辑；使用服务自己的 Key 时设为 `false` 并配置 `env_key`，不同凭据同时存在时单独测试实际选择结果 |
| `wire_api` | 以当前源码支持的协议为准；当前普通提供方使用 `responses`，旧 `chat` 配置已被源码拒绝 |
| 模型与传输能力 | 按服务实际支持情况验证流式输出、工具调用、取消及声明支持的传输方式 |

自定义服务的 Key 不等同于官方 OpenAI Key，不应默认导入主登录缓存。不能把任意所谓兼容接口都承诺为完整可用；提供方接入成功后还要完成编码任务所需的协议验证。不要为了切换服务，把用户的 ChatGPT 凭据自动发送到新地址。

现有 access token、受管理认证和 MCP OAuth 入口也不因鸿蒙移植而无故裁剪；它们按上游支持范围单独登记，并受各自账号及服务条件约束，不以 API Key 测试结果代替。

## 凭据存储怎么适配

首版拟使用文件存储，保留上游认证文件格式及刷新逻辑。检查目录与文件访问权限、并发更新、异常中断和登出清理；不把凭据放进程序安装包、项目仓库或普通日志。

文件模式在实际用户数据目录保存认证文件，它不是鸿蒙系统加密密钥库。对目录和文件的访问限制须在真机上验证，不能仅凭 Mac 上设置了权限就宣称安全存储已完成。升级时保留认证格式和用户目录，重新打开终端后应能读取有效凭据。

`cli_auth_credentials_store = "file"` 仅决定运行行为。已把 `codex-keyring-store` 和 `rmcp-client` 清单中的 Linux Secret Service/keyring 后端限定为非 OHOS。OHOS 的默认密钥存储适配器对读取、保存和删除均返回 `Unsupported`，不会使用 keyring 的内存默认实现伪装成已经持久保存。

此改动保留上游文件存储和 `auto` 模式已有的回退规则；没有把强制要求系统密钥存储的配置偷偷改成文件存储。首版安装方案显式配置主登录和 MCP OAuth 的 `file` 模式。当前凭据模块目标检查及错误行为宿主测试已通过，完整登录链路仍需后续验证。

MCP OAuth 的存储配置与主登录存储分别处理；不因主登录已经可用就宣布所有 MCP 登录可用。后续若集成鸿蒙安全存储，应保留读写、刷新、错误映射、迁移和登出语义，具体 API 在有官方依据后再选定。

## 验收与上游同步

- 无设备：依赖构建、证书解析、代理规则、认证状态机及文件更新的宿主测试。
- 真机：API Key、设备码和浏览器登录分别记录；包含 DNS/TLS、实际模型流式请求、新进程读取、ChatGPT token 刷新、API Key 轮换、退出、断网恢复和权限拒绝。
- 错误必须能区分：网络不可达、证书失败、账号拒绝、凭据无法读取及目标能力不支持。

统一用例及报告要求见[测试规范的认证专项](测试规范.md#5-认证专项)。可复用的现有测试包括 [设备码登录](../../codex-rs/login/tests/suite/device_code_login.rs)、[浏览器回调](../../codex-rs/login/tests/suite/login_server_e2e.rs)、[刷新](../../codex-rs/login/tests/suite/auth_refresh.rs)、[退出](../../codex-rs/login/tests/suite/logout.rs)和[存储](../../codex-rs/login/src/auth/storage_tests.rs)。这些入口说明可以选哪些测试，不表示本轮已执行。

每次上游同步都复查登录参数、客户端和重定向配置、令牌格式、存储策略、提供方认证选择及管理限制；保留修复而不固定复制一套过时认证协议。认证相关合并必须执行受影响回归，并为鸿蒙专用接口保留目标检查和真机验收。

采集日志时只记录必要错误和经过处理的服务信息，不输出 token、完整认证文件或含密钥的请求头；设备码、含 state 的授权链接和回调参数也要脱敏。证书、代理和账号问题不能被笼统归因于“鸿蒙不支持”。
