4. 设备编号不一致的高优先级假设

该构建的 codex-rs/linux-sandbox/src/daemon_mounts.rs 中，daemon_socket_mask_paths 读取 Rust File.metadata().dev()，再调用 libc::major / libc::minor 拼成设备编号字符串。

Cargo.lock 锁定 libc 0.2.186。该版本 src/unix/linux_like/linux_l4re_shared.rs 的规则为：
major = ((dev & 0x00000000000fff00) >> 8) | ((dev & 0xfffff00000000000) >> 32)
minor = (dev & 0xff) | ((dev & 0x00000ffffff00000) >> 12)

对探针观察到的原生 st_dev=66699 做算术计算：
major = 260
minor = 139
得到 260:139，与该目录挂载表的 0:66699 不同。

check_mounts 用 fdinfo/statx 得到的挂载 ID 查找条目，再比较 mountinfo.device 与上述转换结果。现有例外仅覆盖 Btrfs；hmfs 不适用。若失败 Rust 进程读到与 C 探针相同的 dev=66699，该设备编号比较分支会拒绝并产生当前通用错误。

另一个源码线索：bwrap.rs 先检查 a/ 的挂载路径，再检查 s/。a/ 的错误直接传播；s/ 的错误额外带上目录路径。当前日志只有通用错误，与前者失败相符，但仍需实际阶段日志确认。

建议下一版在拒绝前记录：检查目的（aliases/control sockets）、目录路径、Rust metadata.dev() 原值、major/minor 结果、fdinfo/statx 来源及 mount_id、匹配条目的设备编号与文件系统类型、具体拒绝分支。先确认 OHOS hmfs 的 ABI/挂载语义，再设计目标平台适配；不要直接忽略所有设备编号比较。

源码在输出查询结果后记录 native-dlclose，随后调用 dlclose(handle)。崩溃发生在该阶段之后，但当前没有 dlclose 返回后的标记，不能排除其后代码或进程退出过程；应增加细分日志并排查库卸载生命周期。

context_not_exist 应清楚表达 CLI 当前无应用上下文，不能把它描述成 files/cache 实际路径不可访问。目录报告 incomplete_checks=3 对应这三个崩溃，a/s 的 path 工作进程本身均为退出 0。
