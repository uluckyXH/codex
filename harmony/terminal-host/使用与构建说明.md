# 鸿蒙原生终端宿主源码

本目录维护普通调试应用 `com.codex.emulatorhnp`，只声明 INTERNET，通过官方 private HNP 执行原样签名的 Codex。源码、HAP 和诊断不含认证配置；CLI 使用 `platform` 契约和运行时实际身份，不再绑定某台模拟器 UID。App 版本为0.2.0（101）。商业 PC 的独立 HiShell 仍由真机验收，不能由 GUI 的成功替代。

## 目录及首次准备

宿主再次查询原生 ApplicationContext filesDir 并比较 ArkTS 来源，验证完整祖先、归属、权限和对象身份。`prepare` 调用 `codex doctor --initialize-data-directories --json`，有界收集 stdout/stderr，确认返回的 `paths.root` 是 `filesDir/codex`；通用的 state/r/tmp/logs 由 CLI 初始化。宿主随后创建可选 workspace 和 `host/{control,handoff-private,home}`。空白 Shell 无需配置、Key 或登录。

首次平台 base/files 为0777时，严格准备会拒绝。全新应用可直接点“收紧本应用目录”：原生入口先验证完整来源，只收紧当前应用自有的 base/files 到0700，记录修改前后的 owner、group、mode、dev/ino，再调用共享初始化。这是明确的 GUI 操作；CLI 不修改平台父目录，不能把修正后的成功记成独立 CLI 初始0777通过。未能建立日志时，失败详情保留在 UI“查看诊断”。

私有配置仅由显式 `import` 导入：`codex/host/handoff-private/incoming-config.toml` → `codex/state/config.toml`。内容不进入报告，导入后删除对应中转对象。prepare、空白 Shell 和版本不导入配置。操作请求在 `codex/host/control/action.txt`，原生完成标记在 `codex/host/launch-completion.txt`；报告、工具诊断和 Codex 默认日志在 `codex/logs/`。

## 使用终端

空白 Shell 与直接 Codex 是两个独立会话。工作目录可输入绝对路径，留空使用可选 workspace；中文、空格和引号以结构化 argv 传递。普通项目仅检查可进入性，不要求应用所有或0700。PATH 包含已安装程序的 bin、codex-path 和系统目录。空白 Shell 可用 `cd`，再执行 `codex`；正常退出手工运行的 Codex 后回到 Shell。

直接 Codex 固定模型 `gpt-5.6-terra`，新会话按用户明确选择的只读、项目可写或完全访问启动，审批为 on-request；不会自动切到完全访问。系统授权和内核隔离能力仍需单独验证。

“中断当前任务”向当前 PTY 发送终端中断字符，记录前台组查询结果；它不等于关闭 Shell。“退出 Codex”关闭专用 Codex 会话。“关闭当前终端”关闭选中会话和它的作业，不停止另一页签。界面依据实际状态显示正在关闭、已退出或清理未确认。

关闭使用 pidfd 稳定句柄管理所属会话及已观察的后代，TERM后1秒升级KILL。保留直接子进程直到完成成员检查，再 waitpid 回收；5秒仍存活或观察/等待失败会保留失败。成功后原生有界保存64KiB尾部输出并释放 PTY，不依赖网页继续轮询。所有输入、缩放、中断、读写和关闭都校验32字符会话标识。此机制管理普通终端作业；不承诺隔离恶意或未观察的双重fork守护进程。pidfd 或进程观察能力不足时明确拒绝或报告未确认。

进程实际身份来自 `/proc/PID/status`，不从 proc inode owner 推导；dumpable=0可能让 inode 属于 root。读取失败但 status 已证明其他身份、且 PID 未被跟踪时可以排除；已跟踪或身份不明的不可读对象不能当作已退出。需要主会话在设备上核实普通应用可读性和 Codex hardening 后的行为。

## 构建与不编译检查

编译由主会话在确认模拟器关闭后串行执行，Rust 复用 `.harmony-build/current`；HAP 使用实际全英文的 `.harmony-build/terminal-host-current`。下面命令未由终端会话执行。

```sh
# 关闭模拟器并确认退出后，编译纯协议/进程元数据解析测试；不涉及认证和设备。
host_native_dir='/Volumes/MacSSD/Repositories/codex/harmony/terminal-host/entry/src/main/cpp'
host_checks='/Volumes/MacSSD/Repositories/codex/.harmony-build/current/host-checks'
mkdir -p "$host_checks"
/usr/bin/clang++ -std=c++17 -Wall -Wextra -Werror -I "$host_native_dir" \
  harmony/terminal-host/host_protocol_test_main.cpp \
  "$host_native_dir/host_json.cpp" "$host_native_dir/process_identity.cpp" \
  -o "$host_checks/host-protocol-tests"
"$host_checks/host-protocol-tests"

# 单独编译配置传输夹具；运行套件本身不会自动编译。
/usr/bin/clang++ -std=c++17 -Wall -Wextra -Werror -I "$host_native_dir" \
  harmony/terminal-host/config_import_test_main.cpp "$host_native_dir/secure_config.cpp" \
  -o "$host_checks/import-config"
CODEX_CONFIG_IMPORT_TEST_BINARY="$host_checks/import-config" \
  python3 harmony/terminal-host/test_secure_config.py
```

```sh
# 以下仅运行 JS/Python 夹具，不调用编译器、HNP工具、认证或设备。
node harmony/terminal-host/test_terminal_bridge.cjs
python3 harmony/terminal-host/test_prepare_codex_hnp.py
python3 harmony/terminal-host/test_build_terminal_host.py
```

构建需要 DevEco Studio26及完整SDK/Node/Hvigor/OHPM/Java。分发必须已有完整签名和原构建记录，使用 platform、新数据布局和签名 HNP alias 入口；`--with-hnp-alias` 由主会话的分发构建提供。HNP脚本核对完整原校验清单、运行文件及元数据，复制后再次比对，不能只更新一份新的清单掩盖旧二进制。HNP版本同时含 Git SHA 和签名运行文件组合摘要，避免同一 HEAD 的不同未提交构建缓存旧代码。

```sh
# 先关闭模拟器。发行目录替换为主会话已准备的同一份 platform 签名分发。
python3 harmony/terminal-host/build_terminal_host.py \
  --distribution '/实际位置/同一份platform签名分发' \
  --deveco '/Volumes/MacSSD/Applications/DevEco-Studio.app' \
  --output '/Volumes/MacSSD/Repositories/codex/.harmony-build/terminal-host-current' \
  --bundle-name com.codex.emulatorhnp

# 第二个独立应用身份；只重建宿主，Codex及工具ELF直接复用同一分发并逐文件比对。
python3 harmony/terminal-host/build_terminal_host.py \
  --distribution '/实际位置/同一份platform签名分发' \
  --deveco '/Volumes/MacSSD/Applications/DevEco-Studio.app' \
  --output '/Volumes/MacSSD/Repositories/codex/.harmony-build/terminal-host-second-current' \
  --bundle-name com.codex.emulatorhnp.second
```

输出目录必须新建，且解析符号链接后的完整路径也必须符合 Hvigor 的英文字符限制。本机 `current` 指向历史中文缓存，所以 HAP 不能放在其内部；失败尝试保留日志后清理重复产物。HNP 安装版本字段最多31字节（含末尾 NUL 的缓冲区为32字节），当前使用8位源码摘要和12位运行文件摘要，完整摘要仍保存在清单；Codex 对外版本不因此缩短。

输出目录必须新建。仅改复制项目的 bundle 元数据；原源码和签名 ELF 不改写。输出 HAP、SHA256、build-manifest及日志，记录原运行文件摘要、bundle、宿主源码摘要和生成AppScope元数据摘要。两个产物中的 `hnp.runtime_identity` 及每个原运行文件摘要必须一致。HAP使用模拟器允许的调试安装，不意味着商业真机发行证书；两个身份必须读取实际应用 EUID 验收。

## 主会话设备验收顺序

1. 构建完成后再开模拟器，更新默认 bundle，安装全新的第二 bundle，不卸载原应用来换 UID。记录实际两个 EUID 和系统版本。
2. 首次打开第二 bundle，不提供配置：保存原始 base/files 模式和严格 prepare 拒绝；“查看诊断”应显示实际 owner/mode。点“收紧本应用目录”后保存日志中的前后状态，再验证无Key Shell可打开。把这两步分开计结果。
3. 在空白 Shell 执行 `pwd`、`command -v codex`、`command -v rg`、`codex --version`；手工准备带中文、空格和引号的目录，用 cd 和直接启动两种入口核对 cwd。两个会话同时运行，切页签不能重启或停止它们。
4. Shell中运行 `sleep 60` 验证中断返回提示符；再运行后台作业及忽略TERM的子进程，关闭终端并在进程状态/原生报告中确认 KILL、waitpid、零存活和 PTY释放。Codex空闲、真实请求和工具运行的停止分别计项；真实请求由主会话按已有授权和私有配置执行。
5. 把旧token送入本机网页夹具验证拒绝；设备上关闭后重启，旧回调不能影响新会话。测试已有Codex hardening后的proc观察、扫描/信号拒绝、等待失败和重复关闭；失败不能显示已退出。
6. 两个 bundle 的 codex 数据互不混用、同一签名 ELF摘要一致；项目读写与系统授权另计，不自动启用完全访问。商业 HiShell、不同真实GID、内核能力缺口保留待验收。
